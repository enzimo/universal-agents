# Universal Agents message contract, protocol 1

These files describe every message that Universal Agents processes exchange over NATS:
- the signed frame around each message;
- the subjects it travels on;
- who may send and receive it;
- what its body holds.

They are the source of truth. The Python code follows them, and a remote host, another
installation or an outside agent can implement them without reading UA's Python code.

The protocol is labelled `1.0-pre` while the messages are being moved onto it. It becomes
`1.0` when the last kind is live. Until then a fix may change these files under the same
label. Hosts refuse peers whose label differs.

## Layout

| Path | Written by | Content |
| --- | --- | --- |
| `registry.yaml` | hand | the protocol label, refusal codes, and one entry per message kind and operation: delivery class, address, roles, admission, reply, expiry, signing and routing properties |
| `transport.yaml` | hand | streams, consumers, key-value buckets, object store, limits and expiry per delivery class |
| `team-topologies.yaml` | hand | who may send which kinds to whom in each team topology |
| `schemas/` | hand | JSON Schema 2020-12 for the frame, shared values and every body, within the subset below |
| `examples/` | hand, signed by the script | test keys; trust records (`trust/`); messages that must be accepted (`valid/`), and refusal cases that must be refused with a named code at a named place (`invalid/`) |
| `signing-vectors/` | hand, signed by the script | keys, frames, an authority token and a state record with their exact signing bytes and signatures, and refused base64url spellings |
| `generated/` | `scripts/export_message_contract.py` | JSON copies of the YAML files, per-role NATS permissions, the AsyncAPI 3.1 document, the compatibility record and a digest manifest |

The Python models and dispatch tables in `custom_messages/wire/` are generated by the same
script. Examples, trust records and vectors are written by hand without their derived
values: the script fills in public keys, idempotency keys, body digests and signatures,
and builds each invalid example's frame text (`scripts/message_contract_examples.py`). It
signs and derives keys with RFC 8785, SHA-256 and Ed25519 directly rather than through
`custom_messages.wire`, so the tests compare two implementations. Never edit generated files or values: change the sources and
run

```bash
python scripts/export_message_contract.py
```

`--check` regenerates in memory and fails on any difference, and on any file in a generated
folder that the script did not write. `tests/test_message_contract.py` runs it.

The AsyncAPI document defines send and receive operations for every permitted address,
including pool destinations and durable copies. A client must be able to discover the
same delivery choices in AsyncAPI as in the registry.

## Task dispatch and retries

A task id names the work; a frame's `message_id` names one dispatch of it. A new dispatch,
including reassignment after a handback, gets a new `message_id` even when the task id stays
the same. Its key is made from the task id and the message id ("Idempotency keys"). This
keeps the replacement from being discarded as a duplicate of the first dispatch.

The sender saves the signed frame before publishing and retries that saved frame unchanged.
Retries keep the same message id and idempotency key so they cannot enqueue the same dispatch
twice. The task body and task id do not change.

The live contract test (`tests/test_live_message_contract.py`) checks that an acknowledged
task can be dispatched again and that retrying its replacement does not create another
queued task.

## Replies

A task's work context names its `reply_to`: the requester that its results, questions,
progress, claims and reports go to (registry routing `requester`).
- A delegation names the delegating agent; a team-services dispatch names the agent the
  work is for.
- A task the gateway starts for a person names the gateway route (`edge`) that reaches
  them, and so does a run of a person's own schedule: the scheduler takes the route from
  the schedule, and the worker reports to the person directly (team-topologies.yaml fixed
  rules).
- A result or question sent to a gateway route carries the task's `delivery_ref` and
  `conversation_id` from its work context. The gateway resolves the reference from its
  own records; a result for a task it did not start, such as a scheduled run, has
  nothing else to match.
- A kind routed to the requester that has no address for its target goes only to its
  copies: a scheduled run's claims, progress and handbacks reach the team services, and
  its worker tells the person things with `person.notify`.
- `delivery.refused` goes back to the refused frame's sender (routing `sender`): to the
  agent that sent it, or to an outside agent's adapter on the route its task's reply
  target names. A frame another host sent without an agent (gateway, scheduler, team
  services) names no inbox to answer, so its refusal goes to the team services' inbox; they
  record it and tell the person (`person.notify`) when the refused frame was theirs.

The reply target is part of the signed frame, so no reply needs a lookup, a broadcast or
a fallback (plan, section 11A.1).

## Who may talk to whom

`team-topologies.yaml` names the edges a message can travel and, per topology, which edges
each agent role may use. A kind's `topology_edge` lists the edges an agent may send it on.
A receiver works out the edge from its place relative to the sender for the task the
message is about (its thread record): up to the requester, down to the holder or the agent
given the task, sideways to another agent of the team, person to a gateway route, out to an
outside agent or another team. `custom_messages.wire.topology.edge_allowed` checks the edge
against the kind and the sender's role (from its agent session); a message on an edge the
topology does not allow is refused with `delivery.refused`. Work a person gave an agent
directly reports to the person whatever the agent's role. Messages that hosts send without
an agent (gateway, scheduler, team services) are not topology checks.

## Schema subset

Schemas use only what every implementation reads the same way. `tests/test_message_contract.py`
refuses anything else.

- **Keywords:** `$schema`, `$id`, `$ref` (local to this folder), `$defs`, `title`,
  `description`, `type`, `enum`, `const`, `properties`, `required`,
  `additionalProperties: false`, `items`, `minItems`, `maxItems`,
  `minLength`, `maxLength`, `pattern`, `minimum`, `maximum`, `oneOf`, `examples`.
- **Objects** list every property, set `additionalProperties: false`, and require only
  properties they define.
- **Type-specific keywords** (`pattern`, `minLength`, `minimum`, `items` and the others)
  appear only beside the `type` they apply to. Beside `$ref`, `const` or `enum` only
  `type` and annotations (`title`, `description`, `examples`) may appear. Generated models
  would otherwise drop the extra constraint and accept what the schema refuses.
- **Omission** differs from null. A property outside `required` may be absent,
  but its value must satisfy its schema when present. No typed property accepts
  null, and no `const` or `enum` holds null. Generated models use Pydantic's `MISSING`
  value so omitted fields also remain absent when serialized. The runtime requires
  Pydantic 2.14.1 or later.
- **Numbers** are integers only, within ±(2^53 - 1). Decimals travel as strings.
- **Patterns** use only syntax that every common regular-expression engine reads the same
  way, including Python's `re`, Pydantic's validator and ECMAScript: literal characters,
  character classes (without nested `[`), escaped punctuation, groups and `(?:`,
  alternatives inside a group, and quantifiers. They start with `^` and end with `$`, and
  `$` means the end of the value. Shorthand classes (`\d`, `\w`, `\s`), an unescaped `.`,
  other group forms (lookaround, named groups, inline flags), backreferences, word
  boundaries and possessive quantifiers are refused. Python's `re` also lets `$` match
  before a final newline, so a Python validator must refuse a value that ends with one
  (the tests replace a final `$` with `\Z`).
- **Alternatives** (`oneOf`) are objects told apart by a `const` property that every
  alternative requires.
- **Generated names** must be unique: two kinds, definitions or nested objects that would
  produce one Python class name are refused.

## Canonical form and signatures

Frames, authority tokens and state records are each signed with Ed25519 over their own
domain prefix and a newline (`signing_domain`, `authority_token_domain` and
`state_signing_domain` in the registry), followed by the RFC 8785 canonical JSON of the
document without its signature. Both sides sign and verify over the JSON as received,
never over a re-serialized object. A frame's signature covers its authority token,
token signature included, so the token is signed first.

- A document with a repeated key is refused.
- A number written with a fraction or exponent part is refused, even when its value is
  whole (`1.0`, `1e3`): implementations decide by the number's text.
- Nesting is limited to `max_nesting_depth` containers, including the root object.
  The receiver checks the limit before JSON decoding. Very large integer text,
  invalid UTF-8, unpaired Unicode surrogates and a leading byte-order mark are refused
  as `malformed`.
- Timestamps are UTC strings from 1970 to 9999 with exactly three fractional digits,
  such as `2026-10-22T04:30:00.000Z`. They must name real calendar dates and times,
  without leap seconds; the schema's pattern cannot know month lengths, so receivers
  also refuse dates such as 30 February. The generated models check this during form
  validation, before looking up a key, including timestamps inside an authority token.
- Keys, digests and signatures are unpadded base64url, and only the one spelling that
  encoding the bytes produces is accepted. Some decoders, Python's among them, ignore the
  unused low bits of the last character, which would give every signature 16 accepted
  spellings; receivers re-encode and compare.

## Who sent it

A signature proves which key signed; it says nothing about who holds the key or what
the holder may claim. Receivers therefore never take a key or an identity from the
frame. They look both up in signed records that chain to their installation's
authority (`state_records` in the registry, `schemas/state/`):

| Record | Signed by | Says |
| --- | --- | --- |
| authority keys | (given to every host when it joins) | which keys are this installation's authority |
| `certificate` | the installation's authority | host H of installation X signs with key K for teams T, with roles R and agent types A, between two times, at membership and revocation epochs |
| `revocations` | the installation's authority | these certificates are revoked |
| `agent_session` | a team services host of the agent's team | agent G, of type and team role, runs on host H from one time to another |
| `agreement` | the receiver's own authority | installation Y's authority keys, and which of this installation's teams and durable kinds it may use |

Hosts sign frames for the agents they run. There are no per-agent private keys: agents
that share a process could not keep keys from each other, and an agent that moves would
need its key copied. The session certificate gives each agent a checkable identity
instead.

- **Local hosts and agents.** A local installation runs its authority itself and issues
  every record automatically. Each process that sends frames has its own key and
  certificate; each agent gets a session when it starts.
- **Agents and hosts that join later.** A new agent on a known host needs only a session.
  A new host makes its key on its own machine and gets a certificate once an
  administrator approves the key's fingerprint (or automatically, for a local process).
  Receivers change nothing: the new records are enough.
- **Another installation.** Both operators record an agreement with the other side's
  authority keys. That installation's certificates, revocations and sessions verify
  against those keys, its frames use the sender slot `x-<installation>`, and only the
  durable kinds and teams its agreement lists are accepted. How it places its agents
  inside its installation is its authority's statement; the agreement is what makes
  that statement acceptable.

Every record is signed, so where it is stored adds no trust: the edge adapter may copy
another installation's records unchanged into `UA1_CERTS`. A receiver loads agreements,
then certificates, then revocations, then sessions, because a record's signer must
already be known, and keeps the record with the highest `sequence` for each key. For a
frame it checks, in the registry's order:

1. **Certificate (`unknown_key`):** the trust store holds a certificate for the issuer's
   installation, runtime and membership epoch that names the issuer's key id and was
   valid when the frame was issued. Another installation needs an agreement.
2. **Signature and digest** with that certificate's key.
3. **Revocation (`revoked`):** neither the certificate nor the one that signed the
   frame's agent session is revoked, whenever it was revoked and whatever issue time
   the frame gives: a revoked key still stops queued work, because the sender chooses that time.
4. **Epochs (`epoch_too_old`):** the certificate's epochs meet the receiver's minimum
   for that runtime and installation. The frame's own epochs only name the certificate.
5. **Issuer (`wrong_issuer`):** the frame's revocation epoch and team match the
   certificate. A frame that names an agent names its session too, and the session must
   place that agent, of a type the certificate allows, on the signing runtime when the
   frame was issued. A reply must answer the request the receiver sent, from the team
   and agent that request was for.
6. **Sender (`wrong_sender`):** one of the certificate's roles may send the kind to its
   audience's address (for a reply, receive its request; a kind's `senders_by_address`
   narrows some addresses), and another installation's frame stays within its agreement.
   Only the lead receives a frame whose sole sending role is `edge_adapter`, which speaks
   for outside agents: the receiving host states its agent's role (`Receiver.agent_role`),
   and a worker or pool refuses such a frame.

The accepted residual risks:
- A compromised host can speak as the agents placed on it, including agents that moved
  away, for frames dated before the move that are still within their lifetime.
- A key whose certificate ended normally, without being revoked, can still sign frames
  dated inside the certificate's validity, until those dates fall outside the kinds'
  lifetimes (at most 7 days). Suspected theft calls for revocation, not only rotation.

NATS permissions are a second layer, not the identity: queued work outlives the
publisher's connection, the receiver never sees which login published, other
installations do not trust this broker, and all local processes share one login until
phase 3.

## On behalf of a person

An authority token (`authority` in the frame) proves that work acts for a person:
- A gateway or scheduler host signs it with its certificate's key.
- It names its audience: the installation and team the person asked. Only that team
  presents it, copied unchanged down a delegation tree, and only inside frames of the
  token's own installation.
- It is bound to one root task, one command, or one access request (a person's decision
  on it), and lasts at most `authority_token_max_seconds`.
- A scheduled job's run carries a token the scheduler signed with the run's
  `schedule_id`. A run's schedule comes only from there: the work context names no
  schedule, so a host that passes the task on cannot change it, and a run handed back
  and dispatched again keeps it.

A receiver refuses with `bad_authority` a token on a kind whose `authority` is `none`, a
missing token where it is `required`, and a token that is not signed by an unrevoked
gateway or scheduler certificate serving its audience team, names a schedule without a
scheduler's signature, names another team than the frame's issuer, or was not valid when
the frame was issued.

Each kind that takes a token states its `authority_binding`: what the token is bound to,
and with `at` the body field naming that record. The receiver checks such a field
(`task.request`: `/body/work/root_task_id`; `access.resolved`: `/body/request_id`; the
credential and tool setup forms: `/body/root_task_id`). In every case the handler then
checks that the token is bound to the root task, command or request it holds
(`VerifiedAuthority.require_bound_to`), still as `bad_authority`, before its access
decision. Replies carry no token.

## Delivery, expiry and idempotency

Work, requests and events use `ua.v1.<audience team>.<sender slot>.<address>`. The third
token is the destination team. The sender slot is the issuer's runtime, or
`x-<issuer installation>` for a frame from another installation; runtime ids starting with
`x-` or `_` are reserved. The address decides the audience target: `{agent}`, `{pool}` and
`{edge}` addresses deliver to that target with the audience id in the address,
`work.team` and `svc.team.*` to `team_services`, and `evt.*` events to the whole `team`.
For the last two the audience id is the team id. Any receiver in the team accepts a frame
for the whole `team`.

Each reply is also a signed frame, with kind `<operation>.reply`. Its `subject` is the
actual NATS reply inbox, `_INBOX.<requester runtime>.<one or more inbox tokens>`. Its
`audience.runtime` names that requester runtime and `causation_id` names the request. The
inbox is an explicit exception to the sender-slot rule; the frame signature and the
reply rules above still authenticate the issuer. Receivers compare the signed subject to
the arrival subject for both paths. AsyncAPI describes complete frames and references
replies through their inbox channel's message definitions.

The topology owner creates pull consumers. Consumer names join ids with `~`, which ids
cannot contain, so different teams and agents never share a consumer; NATS would silently
change the first consumer's filter. Generated permission templates
(`generated/permissions/<role>.json`) give each host role:
- **publish:** its kinds under its own id, `ua.v1.{team}.{self}.<address>`, to any
  receiver of its team; and for durable work it receives, only the consumer-info,
  next-message and acknowledgement subjects of its own consumers;
- **subscribe:** its own inbox, `_INBOX.{self}.>`, and the request and event subjects of
  the agents it runs;
- **allow_responses:** for roles that answer requests, one answer per request within the
  request class's expiry, instead of any grant on other runtimes' inboxes.

A kind may have several addresses (its own and its `copy_to` copies), each delivering to a
different audience target. A role gets the subscription or consumer grants for one of them
only when it is among the kind's receivers and serves that target (`audience_targets` in
`transport.yaml`): team services receive a task's copy on `work.team`, not the agent and
pool inboxes the same kind also uses.

Before installing permissions, trusted membership code fills `{team}` with each team the
host serves, `{self}` with its runtime id, and repeats each subject for every `{agent}`,
`{pool}` or `{edge}` the host serves. These identity placeholders must never become
wildcards. Clients use `_INBOX.<runtime>` as their inbox prefix. Workers cannot create or delete consumers, read streams, fetch from other
consumers or acknowledge other consumers' work. The live conformance tests prove both
allowed and refused operations.

`transport.yaml` states the broker settings too: the minimum NATS version and the
server-wide JetStream settings under `server`, then each stream and consumer. A delivery
class's `max_expiry_seconds` caps its kinds' `expiry_seconds`; its stream keeps messages
at least that long, and replay records outlive the longest class expiry. The generator
refuses settings that break these rules.

A receiver accepts a frame from `issued_at` (or a later `not_before`) through the earlier
of `expires_at` and `issued_at + expiry_seconds` for its kind, with the end exclusive.
Hosts' clocks may differ by up to `clock_skew_seconds` (8 seconds), so both ends of this
window, and the validity of certificates, sessions, agreements and authority tokens,
allow that tolerance. Replies use their operation's lifetime. The cap keeps
sender-selected expiry within replay-record retention, which outlives the longest class
expiry plus the tolerance.

**Replay.** Verification has no side effects. A receiver that admits a frame records its
replay key (issuer installation, runtime, membership epoch and message id) with its frame
digest (the SHA-256 of what its signature covers), in the same transaction as the
admission. The same frame redelivered is recognised; other content under the same key is
refused as `replayed`.

**NATS headers** copy frame fields for the transport and are compared with the signed
frame; a copy that disagrees is refused as `subject_mismatch`. Every publish sets
`UA-Kind` (the kind) and `UA-Id` (the message id); JetStream publishes of durable kinds
also set `Nats-Msg-Id` (the idempotency key). `traceparent` and `tracestate` are
transport controls and are not compared; `baggage` is dropped at installation boundaries.
A frame read from storage is verified without headers.

**Idempotency keys.** A kind's registry entry lists, under `idempotency`, the JSON
pointers into the frame whose values make its key. The key is the kind, a colon, and the
unpadded base64url SHA-256 of the RFC 8785 JSON array of those values, in order; an
absent optional field is `null`. For example `task.stop` lists `[/body/task_id,
/body/stop_id]`, so its key is `task.stop:` followed by the digest of `[task_id, stop_id]`.
- A reply's key has one part, its request's key: `<operation>.reply:` followed by the
  digest of `[<request key>]`.
- A durable copy adds its audience target as a last part ("Durable copies").
- The array keeps the boundary between ids that contain colons, and the digest keeps every
  key within 128 characters, whatever the ids' lengths; kind names stay within 84.
- Parts name every value that tells two messages apart. A holder numbers its messages per
  task and a new holder starts again, so progress and result keys include the custody
  token as well as the sequence number.

The Python helper is `custom_messages.wire.frame.idempotency_key(kind, *values)`. A
receiver recomputes the key after checking the body and refuses a different one as
`invalid_body` at `/idempotency_key`.

**Durable copies.** Some facts must reach two inboxes. The team services keep each
task's custody record from claims, results, handbacks, progress and hold accounts,
which go first to the task's requester (plan, section 13A.5). `UA1_WORK` is a work-queue
stream: each message goes to one consumer and is deleted once acknowledged, and NATS
refuses a second consumer whose filter overlaps the first. So the team services cannot
read the requester's inbox; a kind's `copy_to` addresses get a second frame:
- the same kind and body, signed by the same sender, for the copy's audience target
  (`team_services` on `work.team`, audience id the team);
- its own `message_id`, and its own key: the kind's parts plus the audience target. The
  stream drops a repeated `Nats-Msg-Id` on any of its subjects within its duplicate
  window, so a copy with its original's key would be lost;
- saved before publishing and retried unchanged, like any durable frame.

Every role serving the copy's target receives it; it does not become a receiver of the
kind. A copy takes no execution slot, is accepted while paused, wakes no model and is
not rendered: the team services record the fact in the custody record. A copy of
`task.result` with its original's key is refused as `invalid_body`.

## Examples

A receiver of the examples is installation `install_example`. It starts from
`examples/trust/anchors.json` and loads every record under `examples/trust/` except
`extra/`. Unless an example says otherwise, the receiver is the frame's audience, running
on the audience's runtime (or any host when the audience names none), with the agent role
its session names when it is an agent; the time is
`2026-10-22T04:30:01.000Z`; the frame arrived on its own subject without NATS headers; the
replay record is empty; and a reply answers the valid example whose message id it names.

Each file in `examples/invalid/` describes one refusal:
- `refusal` and `at`: the code and the JSON pointer of the field the refusal is about
  (empty for the document as a whole); `also` lists the codes of further defects, which
  must not be reported first;
- `base`: the valid example it starts from;
- `changes`: `{"set": <pointer>, "to": <value>}` and `{"remove": <pointer>}` edits; the
  idempotency key is derived again after them unless a change sets it;
- `signing`: `after` (the default) signs again after the changes, `before` keeps the
  base's signature, `stale_digest` signs again but keeps the base's body digest;
  `signed_by` signs with another key; `token_signing: before` keeps the authority token's
  signature; `after_signing` respells a value with the same bytes;
- `text_changes` and `pad_to_bytes`: edits to the serialized text;
- `context`: `receiver` fields, `now`, `arrived_on`, `headers`, `replay` (`digest` held
  for the frame's key), `trust` (`add` and `remove`, relative to `examples/trust/`),
  `minimum_epochs` and `answering` (a valid example, or null for none);
- `frame_text`: the frame exactly as received, written by the script.

Every refusal code except `access_denied` has an example, and every two neighbouring
checks have an example with both defects, so a receiver that checks in another order
fails one.

## Verification

Run `tests/test_message_contract.py` for contract agreement, the examples and hostile
input refusals. `tests/test_live_message_contract.py` starts a separate authenticated
broker, since the role-permission checks require their own users and authorization
file. It uses public fixture signing keys and no operator credentials.

- **Server binary:** `LIVE_TEST_NATS_SERVER` names it and makes the test fail when it
  is missing; the NATS CI job sets it. Without the variable the test uses `nats-server`
  from PATH and skips when there is none. Either way it fails on a server older than
  `server.minimum_version`.
- **Settings:** the broker, stream and consumers are created from `transport.yaml`, and
  the test checks that the server reports the same values back.
- **What it proves:** real publish, pull, acknowledgement and signed inbox replies; a
  result and its team-services copy both stored and pulled by their own readers; a
  scheduled run delivered to a worker pool and its result to the person's gateway route;
  an outside agent's adapter refused when it publishes into a worker pool;
  separate consumers for ids that an `_` separator would have merged; and refusals of
  other consumers' fetches and acknowledgements, consumer creation and deletion, stream
  reads, publishing under another runtime's id, subscribing to another runtime's inbox,
  to stream subjects or to another agent's requests, and writing into another runtime's
  inbox except to answer a request once.

A team `config.yaml` or `debug.env` cannot supply this isolated authorization fixture.

## Versions

Within one protocol label:
- a sender at the same or an older minor is read strictly: an unknown field is a defect;
- a newer minor's unknown optional fields are ignored.

The frame states its minor, so the receiver chooses before reading the body. A change that an
older receiver must understand needs a new major, which brings new subjects and streams.
