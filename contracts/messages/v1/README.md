# Universal Agents message contract, protocol 1

These files describe every message that Universal Agents processes exchange over NATS:
- the signed frame around each message;
- the subjects it travels on;
- who may send and receive it;
- what its body holds.

They are the source of truth. The Python code follows them, and a remote host, another
installation or an outside agent can implement them without reading UA's Python code.

The protocol is labelled `1.0-pre` while the messages are being moved onto it. It becomes
`1.0` when the last kind is live. Until then a fix may change these files under the same
label. Hosts refuse peers whose label differs and, while the label is a pre-release, hosts of
one installation also refuse peers whose contract digest differs ("Versions").

## Layout

| Path | Written by | Content |
| --- | --- | --- |
| `registry.yaml` | hand | the protocol label, refusal codes, and one entry per message kind and operation: delivery class, address, roles, admission, reply, expiry, signing and routing properties |
| `transport.yaml` | hand | streams, consumers, key-value buckets, object store, limits and expiry per delivery class |
| `team-topologies.yaml` | hand | who may send which kinds to whom in each team topology |
| `schemas/` | hand | JSON Schema 2020-12 for the frame, shared values and every body, within the subset below |
| `examples/` | hand, signed by the script | test keys; trust records (`trust/`); messages that must be accepted (`valid/`), and refusal cases that must be refused with a named code at a named place (`invalid/`) |
| `signing-vectors/` | hand, signed by the script | keys, frames, an authority token and a state record with their exact signing bytes and signatures, and refused base64url spellings and public keys |
| `generated/` | `scripts/export_message_contract.py` | JSON copies of the YAML files, per-role NATS permissions, the AsyncAPI 3.1 document, the compatibility record with the contract digest, and a digest manifest |

The Python models and dispatch tables in `custom_messages/wire/` are generated by the same
script. Examples, trust records and vectors are written by hand without their derived
values: the script fills in public keys, idempotency keys, body digests and signatures,
and builds each invalid example's frame text (`scripts/message_contract_examples.py`). It
signs and derives keys with RFC 8785, SHA-256 and Ed25519 directly rather than through
`custom_messages.wire`, so the tests compare two implementations. Never edit generated files or values: change the sources and
run

```bash
python scripts/export_message_contract.py
```

`--check` regenerates in memory and fails on any difference, and on any file in a generated
folder that the script did not write. `tests/test_message_contract.py` runs it.

The AsyncAPI document has one channel per address, listing every kind sent there, and for
each kind a send and a receive operation per destination, named by its audience target
(`send_task_result_edge`). A durable copy's operations are `send_<kind>_copy_<target>` and
carry `x-ua-copy`. Replies share the requester's inbox channel. A client discovers the same
delivery choices in AsyncAPI as in the registry.

## Task dispatch and retries

A task id names the work; a frame's `message_id` names one dispatch of it. A new dispatch,
including reassignment after a handback, gets a new `message_id` even when the task id stays
the same. Its key is made from the task id and the message id ("Idempotency keys"). This
keeps the replacement from being discarded as a duplicate of the first dispatch.

The sender saves the signed frame before publishing and retries that saved frame unchanged.
Retries keep the same message id and idempotency key so they cannot enqueue the same dispatch
twice. The task body and task id do not change.

The live contract test (`tests/test_live_message_contract.py`) checks that an acknowledged
task can be dispatched again and that retrying its replacement does not create another
queued task.

## Replies

A task's work context names its `reply_to`: the requester that its results, questions,
progress, claims and reports go to (registry routing `requester`).
- A delegation names the delegating agent; a team-services dispatch names the agent the
  work is for.
- A task the gateway starts for a person names the gateway route (`edge`) that reaches
  them, and so does a run of a person's own schedule: the scheduler takes the route from
  the schedule, and the worker reports to the person directly (team-topologies.yaml fixed
  rules).
- A result or question sent to a gateway route carries the task's `delivery_ref` and
  `conversation_id` from its work context. The gateway resolves the reference from its
  own records; a result for a task it did not start, such as a scheduled run, has
  nothing else to match, so the gateway refuses one without a delivery reference with
  `delivery.refused` (the schema cannot require it only for gateway routes: an outside
  agent's results carry none). The gateway takes a worker's result for a person as the
  reply the task's signed reply target asked for; only the gateway and the scheduler
  name a gateway route there.
- A kind routed to the requester that has no address for its target goes only to its
  copies: a scheduled run's claims, progress and handbacks reach the team services, and
  its worker tells the person things with `person.notify`.
- `delivery.refused` goes back to the refused frame's sender (routing `sender`): to the
  agent that sent it, or to an outside agent's adapter on the route its task's reply
  target names. A frame another host sent without an agent (gateway, scheduler, team
  services) names no inbox to answer, so its refusal goes to the team services' inbox; they
  record it and tell the person (`person.notify`) when the refused frame was theirs.

The reply target is part of the signed frame, so no reply needs a lookup, a broadcast or
a fallback.

## Who may talk to whom

`team-topologies.yaml` names the edges a message can travel and, per topology, which edges
each agent role may use. A kind's `topology_edge` lists the edges an agent may send it on.
A receiver works out the edge from its place relative to the sender for the task the
message is about (its thread record): up to the requester, down to the holder or the agent
given the task, sideways to another agent of the team, person to a gateway route, out to an
outside agent or another team. `custom_messages.wire.topology.edge_allowed` checks the edge
against the kind and the sender's role (from its agent session); a message on an edge the
topology does not allow is refused with `delivery.refused`. Work a person gave an agent
directly reports to the person whatever the agent's role. A kind whose `topology_edge` is
`none` is not a topology check: it goes to the team services (access requests, refusals),
only hosts send it, or it goes back to a refused frame's sender (`delivery.refused`);
`edge_allowed` allows it. A kind that lead or worker hosts send to an agent, worker pool or
edge address names its edges, and the generator refuses `none` there: the lead's
`agent.pause`, `agent.resume`, `agent.exit`, `agent.status` and `task.probe` travel `down`.
Messages that hosts send without an agent (gateway, scheduler, team services) are not
topology checks either.

## What bodies carry

**Body rules.** A schema cannot say that a list holds no value twice, that one field is
required when others have given values, that a body needs at least one of several
fields, which values a field may hold when others have given values, or that a time ends
within a span of another time. A kind's `body_rules` say it, and receivers check them
right after the schema, refusing as `invalid_body` at the rule's field:
- `{unique: <list>, by: <member>}`: no two items are equal; for object items, no two
  values of the member every item carries, while plain values compare whole;
- `{requires: <field>, when: [{at: <field>, is: <value>}, ...]}`: the field is present
  whenever every condition holds;
- `{any_of: [<field>, ...]}`: at least one is present;
- `{allowed: <field>, values: [...], when: [{at: <field>, is: <value>}, ...]}`: whenever
  every condition holds, the field holds one of the values, and for a list every item
  does; an absent field passes;
- `{ends_within: <field>, of: <field>, seconds: <n>}`: the time in the first field is at
  most `n` seconds after the time in the second, a body field or a frame field such as
  `/issued_at`; an absent field passes. Both sides of the comparison come from the
  sender's clock, so no clock tolerance applies.

**Long text.** `long_text` holds at most 32,768 characters. A result's answer and a
person's answer may instead go as a text file in the object store (`form: file`,
`text_file`); larger text must. The person's own request travels by reference
(`work.root_request`), so instructions written by the lead stay within the limit.

**Passing a result on.** When the lead, or the team services applying the lead's decision
made ahead, passes a subtask's result on "as it is", code copies the subtask's answer and
files into the new result and names the subtask in `forwarded_from_task_id`. The receiver,
often a gateway, never has to look the subtask up.

**Delivery references** are `dr_` and at least 16 random characters, made by the gateway,
so a phone number, chat id or handle can never pass as one. A task's `delivery_mode`
tells the gateway how to deliver: an interactive reply, a scheduled (`cron`) or deferred
message, a heartbeat, or a system schedule's mode.

**Credentials.** A credential field is either visible (`metadata_visible`, of a kind that
is never secret, and may carry its value) or secret (any kind, never a value): the person
or the store fills secret fields in the broker's own form. A template candidate the
broker saves after approval travels as a JSON file in the object store. The broker's
session id is its own random token.

**Access reviews and decisions.** Access requests go to the team services, which hand
access down or ask whoever may decide. A person's review of a change uses the same kinds
("Change reviews", below). They send the gateway an `access.review` to open a
review in its Inbox; a staged change's review card, written by code, goes by reference.
The person's decision returns as `access.resolved`, with the card's choice, note, kept
items, "keep for later tasks" and "may hand it on" boxes. A decision the team services
cannot record (not the person's to decide, request closed) comes back as an
`access.review` in state `refused`, which the Inbox shows; `decided` and `closed` close
the card. The waiting task learns the outcome from `access.decision`, which only the team
services send. It carries what was granted because a worker on another host cannot read
the team's store; it grants nothing the access service has not recorded. When the task's
holder runs on a host whose certificate names its tools, a `granted` or `handed_down`
decision also carries the task's new access list ("Access on remote hosts"). Until the
runtime's access notices move onto this contract, today's notice still carries ids only,
as the repository's `AGENTS.md` says.

**Change reviews.** When another writer changed a stored record while a request worked on
it, the store refuses the request's change with `change_conflict`, which carries a case id
and a brief, or with `needs_person_decision` ("Covered changes"). The task's holder, lead or
worker, may then ask the person the request works for. No model decides, and the lead
never decides for its workers.
1. The holder sends `access.request` whose `what` is `{type: change_review, case_id,
   question}`: the store's case and the agent's question in its own words. It needs no
   `reason`. The task waits for the outcome, as it does for access. The store records with
   each case the request (root task) whose change it refused, and the team services open a
   review only for a case of the asking task's own request; another case gets
   `access.decision` `refused` with code `not_own_case`, so a task cannot put another
   request's case before its person.
2. The team services open the review in the gateway's Inbox with `access.review` in state
   `open`. Its decider is the person the request works for (a `person` decider), never the
   administrators. Its `brief` is a blob reference to the text code wrote from the case:
   what changed, who changed it and when, and the request's own planned values. Its
   choices are `keep_current`, `use_change` and `stop_request`. Body rules refuse a change
   review without a brief, for the administrators, or with access choices, and access
   choices are the only ones other reviews may offer. The review expires two days after
   it opens, or at a scheduled run's next run when that comes sooner.
3. The person's decision returns in `access.resolved`: the choice and an optional note.
   The fields for kept items, hours, "keep for later tasks" and "may hand it on" belong to
   access reviews only. The body does not say which kind of review it decides, so the team
   services refuse a choice the review did not offer, answering with `access.review` in
   state `refused` and code `choice_not_offered`. Every decision the person submits has its
   own `decision_id`, which its key names: the person's corrected decision, sent within the
   stream's two-minute duplicate window after a refused one, is a new message and is not
   dropped as a duplicate.
4. The team services record the decision, then send the waiting task `access.decision`
   with status `change_decided`, carrying the choice and the note, because a host on
   another machine cannot read the team's store. On `use_change` the task sends the same
   change again as a new command: with a new `request_id`, since a repeat of the refused
   command's key would get its stored `change_conflict` back ("Stored outcomes"), and with
   `seen_version` set to the version the brief showed, which `access.decision` carries
   (`seen_version`). The store lets it through once when it comes from the same request
   (its token's root task), changes the same record with the same planned values, the
   record is still at that version, and the case's decision is `use_change`; otherwise the
   task gets a new brief. On `keep_current` the task leaves the record as it is. On `stop_request`
   trusted code stops the request through its normal stop path, which sends one final
   reply.
5. With no decision by the deadline, the review closes as `expired` and the task gets
   status `change_not_decided`: the change was not made. The request continues and says so
   in its reply.
6. A message from the person in that request's thread while the review is open withdraws
   it. The gateway, which sees the person's decisions and messages in the order the
   person made them, does this: it closes the card and sends `access.resolved` with
   `withdrawn_by_message` before it passes the message on. The team services then send the
   task status `withdrawn` by `person_message`. A decision and a withdrawal reach the team
   services in one queue from one sender, and the gateway sends at most one of them for a
   card, so a decision the person made before writing is never undone by the message.

## Schema subset

Schemas use only what every implementation reads the same way. `tests/test_message_contract.py`
refuses anything else.

- **Keywords:** `$schema`, `$id`, `$ref` (local to this folder), `$defs`, `title`,
  `description`, `type`, `enum`, `const`, `properties`, `required`,
  `additionalProperties: false`, `items`, `minItems`, `maxItems`,
  `minLength`, `maxLength`, `pattern`, `minimum`, `maximum`, `oneOf`, `examples`.
- **Objects** list every property, set `additionalProperties: false`, and require only
  properties they define.
- **Type-specific keywords** (`pattern`, `minLength`, `minimum`, `items` and the others)
  appear only beside the `type` they apply to. Beside `$ref`, `const` or `enum` only
  `type` and annotations (`title`, `description`, `examples`) may appear. Generated models
  would otherwise drop the extra constraint and accept what the schema refuses.
- **Omission** differs from null. A property outside `required` may be absent,
  but its value must satisfy its schema when present. No typed property accepts
  null, and no `const` or `enum` holds null. Generated models use Pydantic's `MISSING`
  value so omitted fields also remain absent when serialized. The runtime requires
  Pydantic 2.14.1 or later.
- **Numbers** are integers only, within ±(2^53 - 1). Decimals travel as strings.
- **Values keep their JSON type**, also where a `const` or `enum` names them: `true` is
  not `1`, and `1` is not `true`. A field is read only under the name its schema gives it.
  Generated Python models check both, since Pydantic otherwise lets `1` match a constant
  `True` and accepts a field under its Python name (`from_` for `from`).
- **Patterns** use only syntax that every common regular-expression engine reads the same
  way, including Python's `re`, Pydantic's validator and ECMAScript: literal characters,
  character classes (without nested `[`), escaped punctuation, groups and `(?:`,
  alternatives inside a group, and quantifiers. They start with `^` and end with `$`, and
  `$` means the end of the value. Shorthand classes (`\d`, `\w`, `\s`), an unescaped `.`,
  other group forms (lookaround, named groups, inline flags), backreferences, word
  boundaries and possessive quantifiers are refused. Python's `re` also lets `$` match
  before a final newline, so a Python validator must refuse a value that ends with one
  (the tests replace a final `$` with `\Z`).
- **Alternatives** (`oneOf`) are objects told apart by a string `const` property that
  every alternative requires.
- **Generated names** must be unique: two kinds, definitions or nested objects that would
  produce one Python class name are refused.

## Canonical form and signatures

Frames, authority tokens and state records are each signed with Ed25519 over their own
domain prefix and a newline (`signing_domain`, `authority_token_domain` and
`state_signing_domain` in the registry), followed by the RFC 8785 canonical JSON of the
document without its signature. Both sides sign and verify over the JSON as received,
never over a re-serialized object. A frame's signature covers its authority token,
token signature included, so the token is signed first.

- A document with a repeated key is refused.
- A number written with a fraction or exponent part is refused, even when its value is
  whole (`1.0`, `1e3`): implementations decide by the number's text.
- Nesting is limited to `max_nesting_depth` containers, including the root object.
  The receiver checks the limit before JSON decoding. Very large integer text,
  invalid UTF-8, unpaired Unicode surrogates and a leading byte-order mark are refused
  as `malformed`.
- Timestamps are UTC strings from 1970 to 9999 with exactly three fractional digits,
  such as `2026-10-22T04:30:00.000Z`. They must name real calendar dates and times,
  without leap seconds; the schema's pattern cannot know month lengths, so receivers
  also refuse dates such as 30 February. The generated models check this during form
  validation, before looking up a key, including timestamps inside an authority token.
- Keys, digests and signatures are unpadded base64url, and only the one spelling that
  encoding the bytes produces is accepted. Some decoders, Python's among them, ignore the
  unused low bits of the last character, which would give every signature 16 accepted
  spellings; receivers re-encode and compare.
- A public key that someone else chose must be the canonical encoding of a point of
  Ed25519's prime-order subgroup other than the identity (libsodium's
  `crypto_core_ed25519_is_valid_point`). Key generation always gives one. Under a
  small-order key a forged signature verifies for every message; a non-canonical
  encoding gives a key a second spelling, and a point outside the subgroup lets a
  signature pass one verification rule and fail another. Receivers refuse any other
  key where it arrives, as they refuse a misspelled one: a join's presented key
  (`unknown_key` at `/body/application_key/public_key`), a rotation's new key
  (`invalid_body` at `/body/application_key_rotation/proof`), a certificate's
  application key and an agreement's authority keys (`invalid_body` at the key).
  `signing-vectors/vectors.json` lists such keys in `public_key_refused`.

## Who sent it

A signature proves which key signed; it says nothing about who holds the key or what
the holder may claim. Receivers therefore never take a key or an identity from the
frame. They look both up in signed records that chain to their installation's
authority (`state_records` in the registry, `schemas/state/`):

| Record | Signed by | Says |
| --- | --- | --- |
| authority keys | (in the bootstrap bundle every host starts from) | which keys are this installation's authority |
| `certificate` | the installation's authority | host H of installation X signs with key K for teams T, with roles R and agent types A, between two times, at membership and revocation epochs; it is connected or intermittent, and a remote host's certificate names the tools it may run |
| `revocations` | the installation's authority | these certificates, and their keys, are revoked; signed again at least every 6 hours, and current for at most a day |
| `agent_session` | a team services host of the agent's team | agent G, of type and team role, runs on host H from one time to another |
| `agreement` | the receiver's own authority | installation Y's authority keys, and which of this installation's teams and durable kinds it may use |

Hosts sign frames for the agents they run. There are no per-agent private keys: agents
that share a process could not keep keys from each other, and an agent that moves would
need its key copied. The session certificate gives each agent a checkable identity
instead.

- **Local hosts and agents.** A local installation runs its authority itself and issues
  every record automatically. Each process that sends frames has its own key and
  certificate; each agent gets a session when it starts.
- **Agents and hosts that join later.** A new agent on a known host needs only a session.
  A new host makes its key on its own machine and gets a certificate once an
  administrator approves the key's fingerprint (or automatically, for a local process).
  Receivers change nothing: the new records are enough.
- **Another installation.** Both operators record an agreement with the other side's
  authority keys. That installation's certificates, revocations and sessions verify
  against those keys, its frames use the sender slot `x-<installation>`, and only the
  durable kinds and teams its agreement lists are accepted. How it places its agents
  inside its installation is its authority's statement; the agreement is what makes
  that statement acceptable.

Every record is signed, so where it is stored adds no trust: the edge adapter may copy
another installation's records unchanged into `UA1_CERTS`. A receiver loads agreements,
then certificates, then revocations, then sessions, because a record's signer must
already be known, and keeps the record with the highest `sequence` for each key. For a
frame it checks, in the registry's order:

1. **Certificate (`unknown_key`):** the trust store holds a certificate for the issuer's
   installation, runtime and membership epoch that names the issuer's key id and was
   valid when the frame was issued. A certificate that another one `replaces` counts as
   valid only until `certificate_overlap_seconds` after its replacement was issued.
   Another installation needs an agreement.
2. **Signature and digest** with that certificate's key.
3. **Revocation (`revoked`):** neither the certificate nor the one that signed the
   frame's agent session is revoked, by its id, by its runtime and key id, or by its public
   key, whenever it was revoked and whatever issue time the frame gives: a revoked key
   still stops queued work, because the sender chooses that time.
4. **Current revocations (`revocations_not_current`):** the receiver holds a revocations
   record of the issuer's installation that is current at its clock, within the clock
   tolerance. With none, or only an expired one, it cannot know what was revoked lately,
   so it refuses every frame except installation traffic (join and renewal replies) from
   its own installation authority, which a host needs to renew its certificate. A host
   that reconnects reads the current record first ("Trust over time").

   This refusal is temporary (`temporary` in the registry): the receiver lacks a record,
   and the frame may be valid. It answers a request with it, and never sets queued work
   aside for it, so `revocations_not_current` is no dead-letter reason. A host without a
   current record of its own installation stops pulling queued work until it reads one;
   what it already pulled stays unacknowledged and comes back when it pulls again. A frame
   from another installation whose record is not current is left unacknowledged with a
   negative acknowledgement and a delay of at least a minute, and is set aside only when it
   reaches the consumer's delivery limit (`delivery_limit`).
5. **Epochs (`epoch_too_old`):** for request/reply messages and events, the certificate's
   epochs meet the receiver's minimum for that runtime and installation. Queued work
   (durable and dead-letter frames) is judged by the certificate valid when it was issued
   and skips this step ("Trust over time"). The frame's own epochs only name the
   certificate.
6. **Issuer (`wrong_issuer`):** the frame's revocation epoch matches the certificate, and
   its team is one the certificate serves; installation operations and their replies name
   the installation scope `_install` instead, and no agent. A frame that names an agent
   names its session too, and the session must place that agent, of a type the
   certificate allows, on the signing runtime when the frame was issued. A reply must
   answer the request the receiver sent, from the team and agent that request was for. A
   renewal's body names the certificate that signs it.
7. **Sender (`wrong_sender`):** one of the certificate's roles may send the kind to its
   audience's address (for a reply, receive its request; a kind's `senders_by_address`
   narrows some addresses). A frame from the receiver's own installation is addressed to
   its issuer's team: reaching another team needs a later agreement between teams. Another
   installation's frame stays within its agreement, and comes from that team's lead agent
   (its session's `agent_role` is `lead`) or from its team services speaking for no
   agent: between teams only the leads talk. A host that runs the lead may run workers
   too, so the session decides, not the host's roles.
   Contact with outside agents goes through the lead, in both directions. A frame whose
   sole sending role is `edge_adapter`, which speaks for outside agents, reaches only the
   lead's inbox or the team services: the receiving host states its agent's role
   (`Receiver.agent_role`). An adapter receiving for an outside agent
   (`Receiver.outside`) accepts frames only from a lead agent or the team services.

The accepted residual risks:
- A compromised host can speak as the agents placed on it, including agents that moved
  away, for frames dated before the move that are still within their lifetime.
- A key whose certificate ended normally, without being revoked, can still sign frames
  dated inside the certificate's validity, until those dates fall outside the kinds'
  lifetimes (at most 7 days). Suspected theft calls for revocation, not only rotation.

NATS permissions are a second layer, not the identity: queued work outlives the
publisher's connection, the receiver never sees which login published, other
installations do not trust this broker, and today all local processes share one NATS login
until each process gets its own credential with these permissions.

## On behalf of a person

An authority token (`authority` in the frame) proves that work acts for a person:
- A gateway or scheduler host signs it with its certificate's key.
- It names its audience: the installation and team the person asked. Only that team
  presents it, copied unchanged down a delegation tree, and only inside frames of the
  token's own installation.
- It reaches only the task's holder, in the holder's own queue. A worker pool's queue is
  read by every host that runs the pool, so a `task.request` to a pool carries no token
  (registry `authority_by_address`); its copy to the team services does. When an agent
  claims the task and the team services count the claim ("Claims"), or `custody.decide`
  reassigns it, they record the custody and send the holder `custody.confirmed` on its
  control queue, `work.control.<agent>` ("An agent's two queues"): the task id, its custody
  token and custody window ("Custody windows"), and the task's authority token when the
  work has one. Only these confirmations, reason `claimed` or `reassigned`, carry the
  token; a renewed window or a new access list (`renewed`, `access_changed`) carries none,
  so a window can be renewed after the token has ended.
- It never reaches an outside agent. An outside agent's adapter receives
  `custody.confirmed` at `work.edge.<edge>` without the token, refuses any frame that
  carries one (`bad_authority`), and presents none itself: no binding lists the
  `edge_adapter` role among its senders, which the generator checks.
- It is bound to one root task, one command, or one access request (a person's decision
  on it), and lasts at most `authority_token_max_seconds`. A command token lasts at most
  `command_token_max_seconds` (300 seconds): the gateway signs one for each command, and
  it is useful only for minutes.
- It names no roles: receivers read the person's current roles and standing from the
  team's people records, so a role taken away while a token lasts no longer counts.
- A scheduled job's run has a token the scheduler signed with the run's `schedule_id`;
  the run's holder gets it with the task, or with `custody.confirmed` when the run went
  to a worker pool. A run's schedule comes only from there: the work context names no
  schedule, so a host that passes the task on cannot change it, and a run handed back
  and dispatched again keeps it.
- System work, a run of a schedule that works for no person, carries a scheduler's token
  that names its `schedule_id` and no person. No other token may leave out the person.
  Today's signed context for such a run also names its schedule and no person.

A receiver refuses with `bad_authority` a token on a kind whose `authority` is `none`, or
at an address whose `authority_by_address` is `none` (a `task.request` to a worker pool), a
missing token where it is `required`, and a token that is not signed by a gateway or
scheduler certificate serving its audience team and known to be unrevoked (the receiver
holds a current revocations record), names a schedule without a
scheduler's signature, names neither a person nor a schedule, names another team than the
frame's issuer, lasts longer than its limit, or was not valid when the frame was issued.
It also refuses a token that was not valid when the frame reached it, within the clock
tolerance: for queued work, when the stream stored the frame (`verify_frame(stored_at=)`,
JetStream's message timestamp, which the server sets and the sender cannot); for
requests and events, and for a frame read from storage without that time, by the
receiver's clock. A durable frame dated back therefore cannot carry a token that had
already expired when it was sent, while a person's decision, a stop or a custody
confirmation that waits in a queue past its token's end is still accepted.

**Who may present a token.** A receiver accepts an authority token only from the current
holder of the task the token is bound to, or of a task under that root task, and a
command token only from the command's sender. Tokens also come from those who hand them
on without holding the task: the gateway or scheduler that signed the token and starts
the work, and the team services, which keep custody, give a task's token to its holder
and pass a gateway's command on to an agent's host unchanged. The team services and the
gateway check this against the custody record and the team view, and hosts check it
against the thread record. It is the handler's check, not `verify_frame`'s, because it
needs custody state; the handler refuses as `bad_authority`. A token another host read
from a queue therefore does nothing for that host.

**A run's token.** A worker that claimed a due schedule itself asks for its run's token
with `run_context.sign`. Only a scheduler signs a run's token, so a scheduler
answers it: the scheduler serves the team services' audience at its own address,
`svc.scheduler` (`transport.yaml`), so it never hears the team services' requests.
The scheduler checks the claim against the frame's `issuer.agent`, which the agent's
session confirms; a frame that names no agent is refused as `claim_not_held`. An `ok`
answer carries the token, and its `system_work` is true exactly when the token names no
person.

**Bindings.** Each kind that takes a token states its `authority_binding`: one binding, or
a list of them, one per token type it takes. A binding `{type, at, senders}` says:
- `type`: what the token is bound to (`root_task`, `command` or `access_request`). A token
  of a type the kind does not list is refused.
- `at`: the body field that names that record. The receiver compares the two ids
  (`task.request`: `/body/work/root_task_id`; `access.resolved`: `/body/request_id`; the
  credential and tool setup forms: `/body/root_task_id`; commands: `/body/request_id`, or
  `/body/steer_id` for `tasks.steer`). A command binding always names its field.
- `senders`: the host roles that may present a token of that type, within the senders of
  the frame's address; without it, every sender of that address may. On an operation that
  both the gateway and agents send, such as `memory.delete`, a command token is accepted
  only from the gateway and a root-task token only from agent hosts. An agent host that
  received a person's command token therefore cannot use it there.

Each of these mismatches is refused as `bad_authority`. A binding without `at` names no
body field: the handler checks that the token is bound to the root task it holds
(`VerifiedAuthority.require_bound_to`), still as `bad_authority`, before its access
decision. Four lead operations, `steering.decide`, `intent.set`, `requests.pause` and
`requests.resume`, name a request in their body (`root_task_id`) and keep a binding
without `at`. A lead turn may act only on its own request: the team
services compare `root_task_id` with the token's root task and answer another request
with the typed refusal `not_own_request`, which tells the person to act in that request's
thread, instead of refusing the frame. Replies carry no token.

## Custody windows

Each task has one holder at a time. The team services keep the task's custody record, whose
revision is the custody token, and only a result that carries the current token resolves
the requester's stand-in. Agents stay on the host they are placed on. An agent moves only
by a handover from a connected host, which stops it at a safe point and sends its ledger to
the team services, or after an administrator retires its host. Tasks can move to another
holder, and the custody window says when.

**Every confirmation names a window.** `custody.confirmed` carries `custody_window`. Its kind
follows the `connection_class` in the certificate of the holder's host:
- A `connected` host (the installation's main machine, a server) gets
  `{renewed_by: host_record, seconds}`: standard 300, at least 60 and at most 3,600. The host
  record that the host writes every 20 seconds renews it.
- An `intermittent` host (an edge device, a laptop) gets `{renewed_by: reconnection, ends_at}`:
  standard 5 days after the confirmation, and never more than 7 days after the frame that
  carries it was issued (body rule `ends_within`, refused as `invalid_body` at
  `/body/custody_window/ends_at`). Nothing renews it while the host is cut off.

The team services choose the kind from the certificate of the host that the holder's
placement names. The holder's host checks the kind against its own certificate and refuses
a confirmation of the other kind as `invalid_body` at `/body/custody_window`. This is the
handler's check, not `verify_frame`'s, because it needs the receiving host's own
certificate. The lengths are the team services' choice, the same for every task of one
connection class, so a new length needs no new protocol. The team view's task entry and the
requester's `ledger.fact` (`custody_confirmed`) repeat the window, so the requester's
stand-in knows when the task may move. A window ends at most 7 days after its confirmation,
within the lifetime of every durable kind and of an agent session, so a host that reconnects
inside its window still finds its queued messages and can still sign.

**How each side counts.**
- A `host_record` window lasts `seconds` after the holder's last host record that the store
  acknowledged. The holder counts from that record's `issued_at`, the time on its own clock
  when it wrote it; a write the store did not acknowledge renews nothing. The team services
  count from the same record's `issued_at`, as they read it from the store, and add the clock
  tolerance (`clock_skew_seconds` in `transport.yaml`). So the holder's window always ends
  before the team services may move its task.
- A `reconnection` window ends at `ends_at`. The holder counts by its own clock. The team
  services move the task only once their clock passes `ends_at` plus the clock tolerance.

**When a window ends.** Inside its window a holder acts without asking anyone, connected or
not. When the window ends without renewal, the holder keeps working inside the team but holds
every action that reaches outside the team or cannot be undone (sending, buying, deleting,
publishing) until a new `custody.confirmed` gives it a window. A window that ended is never
revived by the host's next host record: a `host_record` window ends once the holder's host
has had no acknowledged host record for `seconds`, and only a new confirmation restores it.
The team services send `custody.confirmed` with reason `renewed` and a new window, for each
task the holder still holds and only if the task has not moved:
- when a host record of the holder's host comes back after a gap: more than the window's
  `seconds` after the previous record they saw for a `host_record` window, or after the
  previous record expired for a `reconnection` window;
- when they start and find a current host record of the holder's host, since they cannot
  know whether a gap happened while they were stopped;
- for a `reconnection` window, also before it ends while the host's record stays current, so
  an intermittent host that stays online does not lose its window.

They never renew a window while the holder's host has no current host record. Confirmations
and moves reach an agent on its control queue, which its host reads even while every slot is
busy ("An agent's two queues"), so a renewal never waits behind work the agent cannot start
yet.

**Moving a task.** The requester (the lead's model through `custody.decide`, or a team rule)
moves a task to another holder only:
1. after the holder's window ended, by the team services' count above;
2. after the holder handed the task back (`task.handback`);
3. after the holder's host was retired: an administrator revoked its certificate, which the
   revocations record lists, so the host can never act again;
4. by a person's override in the gateway.

Otherwise the team services refuse `custody.decide` with `custody_window_open`. Its
`window_ends_at` is the earliest time the move can succeed by their count, clock tolerance
included; a `host_record` window's end moves later while the holder keeps writing host
records. The refusal is a final outcome: a move after the window is a new command with a new
`request_id`.

**A person's override.** The person the request works for, or an administrator, can move a
task before its window ends, after the gateway has warned them that both holders may then
act. Only the gateway sends this move: `custody.decide` with
`override: {warning_shown: both_holders_may_act}` and the person's command token, bound to
the body's `request_id`. The person comes from the token, never from the body. The team
services answer `not_allowed` when the frame carries no gateway command token, and when the
token's person is neither the request's person nor an administrator by the team's people
records. A lead host presents only root-task tokens, so a lead's model cannot override. The
gateway checks the same before it sends.

**After a move.** The former holder gets `custody.moved`. Whatever it sends later is kept as
late work, which the gateway and the team services recognise by its custody token and the
team view. With these rules, two holders act outside the team at the same time only after a
person's override. `custody.moved` carries the next `sequence` of the task's confirmations,
so a confirmation for the old custody that is delivered after the move, a renewal sent just
before it for example, has a lower sequence and is ignored.

**Claims.** A claim (`task.claimed`, with its copy to the team services) asks for custody;
custody, and with it the person's token, come only from the team services' answer. They
count a claim only when:
1. its frame's agent session places the claiming agent on the sending host (`verify_frame`
   checks this);
2. the task is one they hold a copy of, sent to that agent or to a worker pool that the
   agent's host runs by the team's placements;
3. no other claim for the task's current dispatch is recorded. The first recorded claim
   wins.

A later claimant, for example a second host that received the same pool task after an
acknowledgement deadline passed, gets `custody.moved` with reason `claimed_elsewhere` and
the winner's custody token; it stops the task and sends no result. A claim that does not
count gets no confirmation, and the team services record why. A claim whose task copy has
not been recorded yet stays unacknowledged and is taken again after `ack_wait_seconds`; the
sender publishes the copy first ("Durable copies"), so this happens only when the copy's own
handling failed.

## Access on remote hosts

The access rules decide every tool call an agent makes: the agent side (its role's standard
access, the team's defaults, the task's access, the lasting access of whom it works for, and
what the lead may hand on) and the person side, minus blocks. Hosts on the installation's
main machine read the access store for each call. A remote host cannot read that store and
may be cut off for days, so it decides each call itself, with the same rules, from three
signed lists:
1. **The host's tool list:** `tools` in its certificate, the catalog tools an administrator
   approved with its join ("Installation traffic"). It is an upper limit: an agent on that
   host never runs a tool outside it, whatever its access.
2. **The task's access list** (`task_access_list`): what this task may use there, which the
   team services work out with the same access decision for every tool on the host's list.
3. **The team's block list** (state record `block_list`), which the team services sign into
   `UA1_BLOCK_LIST`.

A call runs only when its tool is on the host's list, the task's access list gives it the
level the call needs (or holds a one-time approval for that exact action), and no block in
the newest block list stops it.

**Which hosts use lists.** A host whose certificate names `tools` decides tool calls from
these lists and never runs a tool outside its list. A host whose certificate names none reads
the access store directly, which only the installation's main machine can, so a remote host
without a list runs no tools.

**The task's access list.**
- `custody.confirmed` carries it as `access_list`, exactly when the holder's host certificate
  names `tools`, renewals included. When access changes without a request, for example a
  grant is taken away, the team services send `custody.confirmed` again with reason
  `access_changed` and the new, smaller list.
- When more access is asked for (`access.request`), a `granted` or `handed_down`
  `access.decision` carries the new list to such a holder. While its host is cut off, the
  asking step waits and the task's other work goes on.
- It names the holder, the task, the person's request (`root_task_id`, the root task its
  authority token is bound to), the person (absent only in system work, whose token names a
  schedule and no person), the holder's host (`runtime`), a `sequence` that rises for each
  new list of the task, and when it was issued and ends: the task's end, at most 7 days after
  `issued_at` (body rule `ends_within`). Each tool comes with its level and `fresh_check`
  mark, which the team services copy from the catalog, so a remote host needs no copy of the
  catalog.
- A one-time approval (`one_time`) is bound to the `action_digest` that the request named.
  The host uses it once and records the use durably before the action. No one else can use
  it, because the list belongs to one holder inside its custody window.
- The holder's host checks, and refuses as `invalid_body` at the field: every tool and
  one-time approval names a tool on its own certificate's `tools`; `holder` is the frame's
  audience agent, `task_id` the body's task, `runtime` the host itself, and `person` and
  `root_task_id` those of the task's authority token. These are handler checks, because they
  need the host's own certificate and the task's token. The holder keeps the list with the
  highest sequence for its task and ignores a lower one.
- The team services' frame signature covers the list, so it carries no signature of its own.

**The block list.**
- One record per team, under the key `<team>`, signed only by the team services and read by
  every host of the team. Its body names the team, its `blocks` and its `people`.
- A block entry follows the access store's blocks: whom it stops (`subject`: everyone in the
  team, an agent type, one agent, a person and so every agent working for them, or the runs
  of one schedule), `tool_id`, and optionally one `operation`. An agent's block carries
  `request` (`root_task_id` and `person`), because it stays inside the request and person it
  was made for; people's and administrators' blocks carry none and apply team-wide. A block
  on a tool set or a role is written as one entry per tool, agent type or person it covers
  when the list is signed, because a remote host cannot read tool sets or who holds which
  role. A block naming an operation the host's tool no longer has stops the whole tool, as
  in the access store.
- `people` gives the standing of people who may no longer have work done for them:
  `disabled` or `removed`, by opaque reference. A host stops that person's tasks as soon as
  it learns, and the gateway and the team services refuse their output when it arrives.
- The team services sign it again with the next sequence at least every `fresh_seconds` (900
  seconds) even when nothing changed, and at once on each change. A newer list may hold
  fewer entries. It states its expiry, at most `max_lifetime_seconds` (7 days) after it is
  written, so a cut-off host keeps using its newest list for its custody window; an expired
  list is refused as `expired`, so a host with no unexpired list runs no tools.
- A connected host watches the record and applies a change within seconds. A host counts a
  list's age from its `issued_at` by its own clock, with the clock tolerance
  (`custom_messages.wire.trust.fresh`). A tool marked `fresh_check` runs only with a list at
  most `fresh_seconds` old, and otherwise waits until the host reconnects; by default these
  are the tools that spend money or publish as the person. Other tools run with the newest
  list the host holds. A block that ends after the list was signed stays in a cut-off host's
  newest list until a newer list arrives, so a cut-off host errs toward refusing.

## Delivery, expiry and idempotency

Work, requests and events use `ua.v1.<audience team>.<sender slot>.<address>`. The third
token is the destination team. The sender slot is the issuer's runtime, or
`x-<issuer installation>` for a frame from another installation; runtime ids starting with
`x-` or `_` are reserved. Team ids and agent types are at most 24 characters and agent
ids at most 32, which keeps a host's credential small ("Credential size"). The address
decides the audience target: `{agent}`, `{pool}` and `{edge}` addresses deliver to that
target with the audience id in the address, `work.team`, `svc.team` and `svc.scheduler` to
`team_services`, and `evt.*` events to the whole `team`. For the last two the audience id is
the team id. Any receiver in the team accepts a frame for the whole `team`.

**One address per receiving service.** Requests do not get a subject per operation. The
team services answer every operation at `svc.team`, the scheduler its one operation at
`svc.scheduler`, an agent's host every control operation at `ctl.agent.<agent>`, and the
installation authority both installation operations at `_install.<sender>.svc`. The signed
`kind` names the operation, and the receiver checks the issuer's roles against the kind's
senders (`wrong_sender`), so NATS no longer refuses a kind a role may not send: the
receiver does, after checking the signature. Every role that receives at a team-wide
address receives every kind sent there, so no service hears requests it does not answer;
the generator refuses a registry that breaks this. Counts per operation come from the
receiving services, not from NATS subjects.

Each reply is also a signed frame, with kind `<operation>.reply`. Its `subject` is the
actual NATS reply inbox, `_INBOX.<requester runtime>.<one or more inbox tokens>`. Its
`audience.runtime` names that requester runtime and `causation_id` names the request. The
inbox is an explicit exception to the sender-slot rule; the frame signature and the
reply rules above still authenticate the issuer. Receivers compare the signed subject to
the arrival subject for both paths. AsyncAPI describes complete frames and references
replies through their inbox channel's message definitions.

The topology owner creates pull consumers. Consumer names join ids with `~`, which ids
cannot contain, so different teams and agents never share a consumer; NATS would silently
change the first consumer's filter. Generated permission templates
(`generated/permissions/<role>.json`) give each host role:
- **publish:** its kinds under its own id, `ua.v1.{team}.{self}.<address>`, to any
  receiver of its team; and for durable work it receives, only the consumer-info,
  next-message and acknowledgement subjects of the consumers it may read;
- **subscribe:** its own inbox, `_INBOX.{self}.>`, and the request and event subjects it
  receives;
- **allow_responses:** for roles that answer requests, one answer per request within the
  request class's expiry, instead of any grant on other runtimes' inboxes.

A kind may have several addresses (its own and its `copy_to` copies), each delivering to a
different audience target. A role gets the subscription or consumer grants for one of them
only when it is among the kind's receivers and serves that target (`audience_targets` in
`transport.yaml`): team services receive a task's copy on `work.team`, not the agent and
pool inboxes the same kind also uses.

**Grants for the agents a host runs.** A lead or worker host receives requests and queued
work only for the agents and pools it runs:
- it subscribes to `ua.v1.<team>.*.ctl.agent.<agent>` for each agent it runs, and its
  permission names exactly those agents;
- agent inboxes, agent control queues and worker pools live in a stream per team,
  `UA1_AGENT_WORK_<team>`, and the host may read and acknowledge only its own agents' and
  pools' consumers there.

A broken-into host therefore cannot read, take or acknowledge work queued for agents on
other hosts, or hear their control requests, and it cannot sign as them either, since every
frame names its agent's session ("Who sent it"). Edge deliveries and the team services'
inbox stay in `UA1_WORK`, read through grants on their exact consumers, so agent hosts reach
neither.

**An agent's two queues.** A host asks for queued work only while it can act on it: it
pulls from an agent's inbox only while the agent can take more work, and stops while the
agent's local waiting list is full or the agent is paused. A message about work the agent
already holds must not wait there behind tasks it cannot start yet: a stop or a hold for
the task that holds the slot, the renewal of its custody window, a smaller access list, or
the access decision or the end of a coordination wait one of its tasks waits for. So each
agent has two queues (`agent_queues` in `transport.yaml`), each with its own consumer in
`UA1_AGENT_WORK_<team>`:
- the **inbox**, `work.agent.<agent>`, holds the kinds that need an execution slot: new
  tasks, results, questions, answers, closed questions, and credential form and tool setup
  results;
- the **control queue**, `work.control.<agent>`, holds every other kind sent to an agent:
  stops, steering, custody moves and confirmations, progress, claims, handbacks, hold
  accounts, reports, access decisions, the ends of coordination waits, refusals and ledger
  facts.

The host reads the control queue whenever it runs the agent, paused or not, and admits each
message at once, since none needs a slot. Like all queued work, it waits only while the
host has no current revocations record of its own installation ("Who sent it"). A paused
agent acts on what it admitted when it resumes, and keeps the work queued in its inbox
(`agent.pause`). The registry's admission follows from this: a kind sent to the inbox needs
an execution slot and is not accepted while paused, and a kind sent to the control queue
needs no slot and is accepted while paused. The generator refuses any other combination,
and each queue refuses the other's kinds (`subject_mismatch`).

The two queues keep no order between them. Messages about one task carry their own sequence
numbers ("Custody windows", "Idempotency keys"), and a redelivered message can arrive after
later ones anyway. When a host starts reading an agent, after a restart or a move, it reads
the control queue until nothing is pending there before it pulls from the inbox, so it
records the facts about tasks the agent holds or delegated before the work that follows
them. A stop, a steer or a confirmation can also come before its task: a task reassigned to
an agent is confirmed to it at once, while its `task.request` may still wait in the inbox.
The host records such a message under its task id and applies it when the task arrives, so
a task stopped before it started never starts; it forgets the message once the message's
own lifetime ends. Worker pools need no second queue, since a pool receives only new tasks.
An edge's reader, a gateway route or an outside agent's adapter, passes each message on and
runs no task itself, so it reads its one queue whenever it runs.

**Waking the model.** Each kind's `wakes_model` says what a message does to the model of the
agent that receives it:
- `always`: the host gives the task a model turn as soon as it can. A task paused on a local
  wait (a Strands interrupt) resumes, and a task with no turn running gets one;
- `next_turn`: the model sees the message at the task's next turn, together with other news.
  It starts no turn;
- `never`: the message only changes records, such as the work ledger or custody.

A kind that ends a local wait is `always` wherever it ends it, since resuming the paused tool
call continues the model's turn: an access decision (except `waiting`, which leaves the wait
open), a tool setup's result and the end of a coordination wait. A credential form's result
ends no local wait: the lead goes on, and sees the result at its next turn.

**Credentials follow placement.** A host's NATS credential names the agents and pools it
runs, so it changes when the host gains or loses one. NATS checks a user's permissions only
when it connects, and acknowledgements are not signed, so a credential that names an agent
must stop working before another host reads that agent's queue. An agent moves in this
order:
1. The old host stops pulling the agent's inbox and answering its control address. It
   keeps reading the agent's control queue while it finishes, or hands back with
   `task.handback`, every task it admitted, and acknowledges their messages while its
   credential still names the agent; then it stops reading the control queue too. The
   handover sends the agent's ledger to the team services ("Custody windows").
2. The old host renews (`host.renew`) and connects with the credential of the reply, which
   no longer names the agent. The installation authority then revokes every credential for
   the host's NATS key issued before that one: the NATS account's revocation list names the
   key with the new credential's issue time, which also closes any connection still using
   an old credential.
3. Only then do the team services write the new placement, and the new host gets a
   credential that names the agent. Work queued for the agent stays in the agent's
   consumers, and the new host reads it.

A host that is cut off or retired cannot take step 1. The authority revokes its credential
first (with its certificate, when an administrator retires it), and the work it admitted
without acknowledging comes back to the agent's queues after `ack_wait_seconds`, where the
new host takes it; its custody moves by the rules of "Custody windows". A credential never
outlives the certificate it comes with: a join or renewal reply whose `connection` ends
after its certificate is refused (`invalid_body` at `/body/connection/expires_at`).

**Credential size.** A credential grows with the agents its host runs: each hosted agent
adds seven subjects (the info, next-message and acknowledgement subjects of its inbox's and
its control queue's consumers, and its control address), 836 bytes of permission JSON with
the longest team and agent ids (24 and 32 characters), which a NATS user JWT's base64url
encoding turns into about 1,115 bytes. Each worker pool adds three subjects, 349 bytes with
a 24-character agent type. `tests/test_message_contract.py` recomputes these figures from
the generated templates. A credential is at most `max_credential_bytes` (65,536 bytes,
`transport.yaml`), the `jwt` field's limit, so the authority places no more agents and
pools on one host than its credential can name: with the longest ids, about 50 agents
beside 10 worker pools. The id caps exist for this; with 64-character ids a host held about
25. A certificate's `session_limit` does not lift that limit. NATS reads a user JWT in the
client's `CONNECT` line, which the server's `max_control_line` limits (4,096 bytes unless
configured), so an installation's servers set `max_control_line` above
`max_credential_bytes` plus the rest of the `CONNECT` line.

**Filling the templates.** Before installing permissions, trusted membership code fills
each role's templates for the host (`custom_messages.wire.permissions.host_permissions`):
- `{self}` becomes its runtime id;
- a subject that names `{agent}`, `{pool}` or `{edge}` is repeated for each agent and pool
  the host runs and each edge it serves, with `{team}` set to that agent's, pool's or
  edge's own team. A host that serves two teams and runs team A's `researcher` therefore
  gets no grant on team B's `researcher`;
- any other subject with `{team}` is repeated for each team the host serves.

These placeholders never become wildcards. Clients use `_INBOX.<runtime>` as their inbox
prefix. Hosts cannot reach another host's, another team's or another role's consumers, and
cannot read streams directly, except the team services, which read their own team's agent
stream to withdraw work. Only the two roles below create, change or delete JetStream
objects or messages. The live conformance tests prove both allowed and refused operations.

**Who sets up the streams.** The topology owner (`topology_owner` in `transport.yaml`) is
the installation authority. It already decides which hosts serve which teams, agents and
pools, since it issues their certificates and credentials, so it knows when a team, agent
or pool appears or leaves, and it runs no model. It creates a team's stream with the team,
and each agent's or pool's consumer with the agent or pool. Its generated grants create,
update and inspect every stream, and create, inspect and delete every consumer of them:
consumer names are a wildcard for it, and membership code fills `{team}` with every team of
the installation.

**Withdrawing queued work.** The team services withdraw a task queued for one of their
team's agents or worker pools by deleting its message from `UA1_AGENT_WORK_<team>`
(`withdrawal` in `transport.yaml`); no other role may. Only the publisher learns a
message's stream sequence, and the task's copy names the task (`task_id`) but neither the
agent or pool its frame went to nor that frame's message id, so the team services find it
themselves:
1. They read their own team's stream from its first sequence, across the team's work
   subjects (`$JS.API.STREAM.MSG.GET` with `next_by_subj` set to `ua.v1.<team>.*.work.>`).
2. They verify each `task.request` frame they find (its `UA-Kind` header names the kind)
   and delete, by its sequence (`$JS.API.STREAM.MSG.DELETE`), every one whose body names
   the task: a task handed back and dispatched again can wait there more than once.

The stream holds only their team's messages, so neither grant reaches another team, and
the generator allows withdrawal only from per-team streams. Work queued for an outside
agent or a gateway route waits in the shared `UA1_WORK`, where they have neither grant:
they stop it with `task.stop` to that edge instead.

A delete can come too late. A host may already have pulled the message without
acknowledging it: NATS still deletes it, and the host starts the task. A holder claims a
task before it acts outside the team, to get its custody window ("Claims"), and the team
services answer the claim of a withdrawn task with `custody.moved`, reason `withdrawn`, so
the host stops it and sends no result. They record the withdrawal in the task's custody
record, so anything the host sends later is late work.

`transport.yaml` states the broker settings too: the minimum NATS version and the
server-wide JetStream settings under `server`, then each stream and consumer. A delivery
class's `max_expiry_seconds` caps its kinds' `expiry_seconds`; its streams keep messages
at least that long, and replay records outlive the longest class expiry. Each durable and
dead-letter address is stored in exactly one of its class's streams, no stream stores
requests or events, and stream subjects never overlap, which NATS would refuse. A stream
named with `{team}` exists once per team and stores only that team's subjects. The
generator refuses settings that break these rules.

A receiver accepts a frame from `issued_at` (or a later `not_before`) through the earlier
of `expires_at` and `issued_at + expiry_seconds` for its kind, with the end exclusive.
Hosts' clocks may differ by up to `clock_skew_seconds` (8 seconds), so both ends of this
window, and the validity of certificates, sessions, agreements and authority tokens,
allow that tolerance. Replies use their operation's lifetime. The cap keeps
sender-selected expiry within replay-record retention, which outlives the longest class
expiry plus the tolerance.

**Replay.** Verification has no side effects. A receiver that admits a frame records its
replay key (issuer installation, runtime, membership epoch and message id) with its frame
digest (the SHA-256 of what its signature covers), in the same transaction as the
admission. The same frame redelivered is recognised; other content under the same key is
refused as `replayed`.

**NATS headers** copy frame fields for the transport and are compared with the signed
frame; a copy that disagrees is refused as `subject_mismatch`. Every publish sets
`UA-Kind` (the kind) and `UA-Id` (the message id); JetStream publishes of durable kinds
also set `Nats-Msg-Id` (the idempotency key). `traceparent` and `tracestate` are
transport controls and are not compared; a sender keeps `tracestate` within 512 characters,
the length W3C Trace Context asks every system to pass on. Senders set no other header,
`baggage` included. A frame read from storage is verified without headers.

**Header size.** JetStream counts headers in a stream's maximum message size. The largest
header block these five headers allow, in NATS's `NATS/1.0` header format, is 891 bytes;
`max_header_bytes` in `transport.yaml` is 1,024, which leaves room for a header a client
library adds to a JetStream publish, such as `Nats-Expected-Stream`. A sender refuses to
publish headers larger than `max_header_bytes`. Every stream's `max_message_bytes` is
`max_frame_bytes` plus `max_header_bytes`, so a frame of the full size is stored with its
headers. The generator checks both.

**Idempotency keys.** A kind's registry entry lists, under `idempotency`, the JSON
pointers into the frame whose values make its key. The key is the kind, a colon, and the
unpadded base64url SHA-256 of the RFC 8785 JSON array of those values, in order; an
absent optional field is `null`. For example `task.stop` lists `[/body/task_id,
/body/stop_id]`, so its key is `task.stop:` followed by the digest of `[task_id, stop_id]`.
- A reply's key has one part, its request's key: `<operation>.reply:` followed by the
  digest of `[<request key>]`.
- A durable copy adds its audience target as a last part ("Durable copies").
- The array keeps the boundary between ids that contain colons, and the digest keeps every
  key within 128 characters, whatever the ids' lengths; kind names stay within 84.
- Parts name every value that tells two messages apart. A holder numbers its messages per
  task and a new holder starts again, so progress and result keys include the custody
  token as well as the sequence number; result keys also name the sending agent, because
  two agents can refuse one task before either holds it, and the team services pass
  results on in their own numbering. A refusal's key names its sender, because several
  receivers can refuse one frame. The team services send several custody confirmations
  for one custody token (a renewed window, a new access list), so a confirmation's key
  names its sequence too. A move's key names the task and the same sequence, since two
  claimants that lost can be told under one custody token.

The Python helper is `custom_messages.wire.frame.idempotency_key(kind, *values)`. A
receiver recomputes the key after checking the body and refuses a different one as
`invalid_body` at `/idempotency_key`. What the receiver of an operation keeps under its
key, and for how long, is in "Stored outcomes".

**Durable copies.** Some facts must reach two inboxes. The team services keep each
task's custody record from claims, results, handbacks, progress and hold accounts,
which go first to the task's requester. The work streams are
work-queue streams: each message goes to one consumer and is deleted once acknowledged,
and NATS refuses a second consumer whose filter overlaps the first. So the team services
cannot read the requester's inbox; a kind's `copy_to` addresses get a second frame:
- the same kind and body, signed by the same sender, for the copy's audience target
  (`team_services` on `work.team`, audience id the team). A copy of a `task.request` to a
  worker pool carries the task's authority token, which the pool frame may not ("On behalf
  of a person");
- its own `message_id`, and its own key: the kind's parts plus the audience target. A
  stream drops a repeated `Nats-Msg-Id` on any of its subjects within its duplicate
  window, and an edge delivery and its copy share `UA1_WORK`, so a copy with its
  original's key would be lost;
- saved before publishing and retried unchanged, like any durable frame;
- published before the frame for the agent, pool or edge, which the sender publishes only
  after the stream acknowledged the copy, so the team services hold a task before anyone
  can claim it ("Claims").

The team services read it there, and no other role does: the scheduler serves the same
target only to answer `run_context.sign`. A copy's reader does not become a receiver of the
kind. A copy takes no execution slot, is accepted while paused, wakes no model and is
not rendered: the team services record the fact in the custody record. A copy of
`task.result` with its original's key is refused as `invalid_body`.

## Examples

A receiver of the examples is installation `install_example`. It starts from
`examples/trust/anchors.json` and loads every record under `examples/trust/` except
`extra/`. Unless an example says otherwise, the receiver is the frame's audience, running
on the audience's runtime (or any host when the audience names none), with the agent role
its session names when it is an agent; the time is
`2026-10-22T04:30:01.000Z`; the frame arrived on its own subject without NATS headers; the
replay record is empty; and a reply answers the valid example whose message id it names.
Joins, renewals and host records carry the fixed example digest
`c734d95cdcb5b0081997c039906cf13cf3eeef0e0ef105160fb1138c5f6a2f60`, not the digest of the
contract they belong to, which would change with them, and the examples' receivers run that
digest. A `protocol_mismatch` answer names another one, the authority's in that example.

Each file in `examples/invalid/` describes one refusal:
- `refusal` and `at`: the code and the JSON pointer of the field the refusal is about
  (empty for the document as a whole); `also` lists the codes of further defects, which
  must not be reported first;
- `base`: the valid example it starts from;
- `changes`: `{"set": <pointer>, "to": <value>}` and `{"remove": <pointer>}` edits; the
  idempotency key is derived again after them unless a change sets it;
- `signing`: `after` (the default) signs again after the changes, `before` keeps the
  base's signature, `stale_digest` signs again but keeps the base's body digest;
  `signed_by` signs with another key; `token_signing: before` keeps the authority token's
  signature; `proof_signing: before` keeps a renewal's new-key proof;
  `record_signing: before` keeps the signature of a state record the body carries
  (a reply's certificate); `after_signing` respells a value with the same bytes;
- `text_changes` and `pad_to_bytes`: edits to the serialized text;
- `context`: `receiver` fields, `now`, `stored_at` (when a stream stored a queued frame),
  `arrived_on`, `headers`, `replay` (`digest` held for the frame's key), `trust` (`add` and `remove`, relative to `examples/trust/`; the
  receiver keeps its records at `now`), `minimum_epochs` and `answering` (a valid example,
  or null for none);
- `frame_text`: the frame exactly as received, written by the script.

`examples/state/invalid/` describes refusals of state reports the same way, from a valid
record under `examples/state/valid/`. Its `context` may add or remove trust records, set
`minimum_epochs`, replace `now`, and name the record the reader `held` (sequence and
digest); `document_text` is the record as stored. The script also fills each valid host
record's certificate digest.

Every refusal code except `access_denied` has an example, and every two neighbouring
checks have an example with both defects, so a receiver that checks in another order
fails one. Every kind has a valid and an invalid example, and every alternative of a body
(each constant that tells a `oneOf` apart) appears in a valid example; the tests check both.

## Verification

Refusal examples check one frame against a starting context. Tests of trust updates
also keep the same store between checks: the late-revocation test first verifies a
frame, adds a revocation, then verifies that the frame is refused. Starting with an
already-revoked certificate cannot check that sequence. Missing header copies and
mismatched header copies have separate refusal examples.

Run `tests/test_message_contract.py` for contract agreement, the examples and hostile
input refusals. `tests/test_live_message_contract.py` starts a separate authenticated
broker, since the role-permission checks require their own users and authorization
file. It uses public fixture signing keys and no operator credentials.

- **Server binary:** `LIVE_TEST_NATS_SERVER` names it and makes the test fail when it
  is missing; the NATS CI job sets it. Without the variable the test uses `nats-server`
  from PATH and skips when there is none. Either way it fails on a server older than
  `server.minimum_version`.
- **Settings:** the broker, stream and consumers are created from `transport.yaml`, and
  the test checks that the server reports the same values back.
- **What it proves:**
  - real publish, pull, acknowledgement and signed inbox replies;
  - a host pulling and acknowledging only its own agents' queues, and reading work queued
    before an agent moved to it once it holds the credential that names that agent;
  - a custody confirmation read from the agent's control queue while new tasks wait unread
    in its inbox;
  - a relayed queue request sent straight to an agent by the gateway: NATS delivers it,
    and the agent's host refuses it as `wrong_sender`;
  - a result and its team-services copy both stored and pulled by their own readers;
  - a scheduled run delivered to a worker pool, and its result to the person's gateway route;
  - a new host that holds only the pre-join permissions joins, and checks the authority's
    reply from its bootstrap records;
  - dead-letter raw copies and notices stored under the receiver's own id;
  - separate consumers for ids that an `_` separator would have merged;
  - the topology owner creating and changing streams, and creating and deleting consumers,
    with its own grants, and the team services finding a queued task in their own team's
    stream by its task id and withdrawing it;
  - a full-size frame stored with the largest headers senders may set;
  - refusals of: another host reading or deleting in the team's stream, and the team
    services deleting in the shared `UA1_WORK`; an outside agent's adapter publishing into a
    worker pool; fetches and acknowledgements on another host's agent consumer, another
    team's stream or the team services' consumer; consumer creation and deletion; stream reads; publishing under
    another runtime's id, dead-letter copies included; subscribing to another runtime's
    inbox, to stream subjects, to the team services' requests or to another host's or
    another team's agents; writing into another runtime's inbox except to answer a request
    once.

A team `config.yaml` or `debug.env` cannot supply this isolated authorization fixture.

## Trust over time

A queued message can wait days, for example while a host is cut off.
- **Certificate at issue time.** Receivers verify every frame and state record with the writer's certificate that was valid when it was issued, even if that certificate has expired since.
- **Revocation.** A certificate on the installation's revocations record refuses all of its frames and records, whenever it was revoked, and so does every other certificate with its key: of its runtime with its key id, or of its installation with its public key under any key id or runtime. Revoking a certificate revokes its key. The authority issues no certificate for a revoked key, so the certificates that hold it are known when it is revoked.
- **The revocations record expires.** The installation authority signs it again with the next sequence at least every 6 hours and at once on each revocation, and each version is current for at most 24 hours (registry `max_lifetime_seconds`; its body's `expires_at`). A receiver without a current record of an installation refuses that installation's hosts, except installation traffic from its own installation authority, and waits for a current record (`revocations_not_current`, "Who sent it"). Hosts store the newest record they verified and never accept a lower sequence, also after a restart: a restarted host adds its stored record before any it reads from `UA1_CERTS`, so an older copy written back to the bucket is ignored. The edge adapter copies another installation's record, which that installation's authority signs again on the same schedule.
- **Entries leave the record.** Each entry names `key_expires_at`: when the last certificate with its key ends, its own or a renewal's that kept the key. An entry may leave once that time plus `replay_ledger_retention_seconds` (30 days and a minute, longer than any frame lasts) and the clock tolerance have passed: by then nothing its key signed can still be accepted. An entry that left with only its own certificate's end would let a renewal with the same key and a later end sign again. Receivers accept a newer record with fewer entries; the revocation epoch still never falls. A receiver that holds an entry a newer record leaves out earlier keeps it until that time and logs a warning (`TrustStore.add`).
- **Sequences never go back.** Readers keep the highest sequence of the revocations record and of the block list, also across restarts. A writer therefore takes each new sequence above the highest it finds in the record's bucket and at least the record's `issued_at` in milliseconds since 1970. An installation authority or team services host restored from a backup, or rebuilt with empty storage, then still writes above every record it wrote before, and receivers do not refuse its records as `replayed` until the record they hold expires.
- **Epochs.** The receiver's minimum membership and revocation epochs apply to certificate-authenticated request/reply messages and events only. Queued work is never refused for an old epoch. Joining proves key possession without a certificate, so a join's epoch zero is accepted on retries after the key becomes known; revocation still refuses the key.
- **Renewed certificates.** Every renewal, with or without a new key, gets a certificate at a higher membership epoch that names the old one in `replaces`. The old certificate stays in `UA1_CERTS` for queued work, but signs new frames only until `certificate_overlap_seconds` (5 minutes) after its replacement was issued, so frames already on their way when a host renews are still accepted. A receiver that wants the old epoch gone for requests and events sooner raises its minimum epoch.
- **Expiry.** Each delivery class has an expiry in `transport.yaml`. Receivers keep their replay record at least as long as the longest expiry.
- **Longest lifetime.** A record is written at its document's `issued_at`. A certificate, agent session, agreement or revocations record ends no later than its record's `max_lifetime_seconds` (registry `state_records`: 90 days, 7 days, 366 days and a day) after it is written; a later end is refused (`invalid_body` at the body's end). A record that must last longer is renewed. A rewrite is written no earlier than the version it replaces. A receiver keeps a trust record with its clock (`TrustStore.add(data, now=...)`) and refuses one dated ahead of it by more than the clock tolerance (`not_yet_valid` at `/issued_at`), so the lifetime counts from a time that has come.
- **Forgetting.** A receiver forgets an agent session or agreement once its newest version was written longer ago than its `max_lifetime_seconds` plus `replay_ledger_retention_seconds` and the clock tolerance (`TrustStore.forget(now)`, at least daily). A certificate is kept an agent session's `max_lifetime_seconds` and the clock tolerance longer, since a session it signed may arrive as late as the certificate's end. By then every version of the record has ended and every frame it vouched for has expired, so the store stays bounded. A forgotten record is not taken back: the store ignores a record it would forget when it holds none under that key, so an older version cannot return either.
- **Revoked certificates are kept.** The revocations record is never forgotten, nor is any certificate it lists, so a join or rotation that names a revoked key stays refused while its entry lasts; the record's 2,000 entries bound them. A certificate whose entry left the record is forgotten like any other. Once a certificate that is not revoked is forgotten, its key id is no longer known, and a join or rotation that names it is judged as a new key. Writers delete a record from `UA1_CERTS` once receivers forget it, and keep revoked certificates there.
- **State reports outlive certificates.** Agent, placement and team-view records do not expire, but a receiver that forgot the certificate that signed one refuses it as `unknown_key`. Their writers write them again under a current certificate before an old one is forgotten, for example when a renewal's overlap ends.

## Installation traffic

Joining an installation and renewing a certificate use the address `ua.v1._install.<sender>.svc`. Their frames name the scope `_install` (`transport.yaml` `installation_scope`) as both the issuer's and the audience's team, and never an agent.

**Starting a host.** A new host starts from a bootstrap bundle that an administrator, or the local installation itself, gives it. The bundle holds:
- the installation's authority keys;
- the certificates of the installation authority's hosts, so the host can check the authority's replies before it has a certificate of its own, and the installation's revocations record. The authority's replies need no current record, so a bundle older than a day still lets the host join; the host reads the current record before it accepts other hosts' frames;
- the NATS credential of the pre-join permission set, `generated/permissions/joining_host.json`. With it the host can publish its own installation requests and read its own reply inbox, and nothing else. Of those requests only a join can succeed: a renewal needs a certificate the host does not have yet (`unknown_key`).

**Joining.** A new host has no certificate yet. It signs `host.join` with the key the request presents; the registry marks this as `verification: proof_of_possession`, and it applies to that one operation only. A receiver checks:
- the join comes from the receiver's own installation and names, as its issuer's key, the key its body presents, which is not an authority key (`unknown_key`);
- a key id the trust store already knows keeps its public key (`unknown_key`), and a revoked one stops the join (`revoked`), as does a public key that a revoked certificate holds under any key id (`revoked`, at `/body/application_key/public_key`);
- the issuer names `_install`, no agent, epoch zero and a runtime id that does not start with `x-` or `_`, and the body asks for that runtime in that installation (`wrong_issuer`);
- the body asks only for roles among the kind's senders, never the installation authority's (`wrong_sender`).

These comparisons, and a renewal's comparison with its certificate, read the body's fields as received, before the body schema: a missing or mistyped field counts as another value (`examples/invalid/host-renew-without-certificate-id.json`).

The authority does not answer a join with a fresh challenge to sign. A join frame lasts 30 seconds, the receiver's replay record refuses other content under its message id, and its retry key names the runtime, key and join id. A copied join can therefore only repeat the same request within its lifetime, and the certificate it gets back is useless without the private key.

**What the authority decides.** An administrator approves the key's fingerprint, or the installation approves a local process automatically; until then the reply is `pending`. A join for a runtime that already holds an unexpired certificate under another key is a lost-key recovery: an administrator approves it again, and the new certificate gets a higher membership epoch and `replaces` the old one. A join's certificate grants at most the teams, roles, agent types and sessions it asked for.

**Connection class and tools.** A join states the host's `connection_class` (`connected` or `intermittent`, "Custody windows") and, for a host that decides tool calls from signed lists, the `tools` it can run ("Access on remote hosts"). Tool ids the catalog lacks, such as a local device's, are the host's proposal: the administrator reviews them with the join. The catalog's entries are records of the access store, not messages, so approving a proposal adds the entry there. The certificate names the connection class the join asked for and at most the tools it asked for, each once. A host whose connection class or tool list must change sends a new join under the key it holds, which an administrator approves like a lost-key recovery: its certificate gets a higher membership epoch and `replaces` the old one.

**Renewing.** A host renews with `host.renew`, signed by the certificate it renews; the body names that certificate and its membership epoch. Every renewed certificate has a higher membership epoch than the one it replaces and names it in `replaces` ("Trust over time"). A renewal carries no connection class or tools: the renewed certificate keeps those of the certificate it replaces, and changing them needs a new join. A host whose reply was lost retries with the same renewal id while the old certificate still signs, or reads its new certificate from `UA1_CERTS`.

**Replies.** A success reply carries the signed certificate (`certificate-document.schema.json`), which only an authority key writes, and a connection credential. The receiver verifies the certificate and refuses the reply as `invalid_body` at `/body/certificate/...` when:
- it does not verify against the installation's own authority keys, or its record's `expires_at` differs from its body's;
- it is for another installation or another runtime than the host that asked;
- a join's certificate names another application or NATS key than the join presented, grants more teams, roles, agent types or sessions than it asked for, names another connection class, or names tools the join did not ask for;
- a renewal's certificate does not replace the certificate that signed the renewal, does not have a higher membership epoch, names another key than the rotated one (or, without a rotation, the kept one), or another NATS key than the new one asked for (or the kept one), or changes the connection class or tools of the certificate it replaces;
- the certificate names a tool twice.

The host then keeps the certificate with `TrustStore.add`. Later requests are verified as usual.

**Identifiers.** `profile_sha256` is the unpadded base64url SHA-256 of the runtime profile the host asks for: the document listing the subjects, agent types and limits an administrator reviews before approving the join or renewal. A join and a renewal state the profile asked for, and the certificate states the profile granted. This contract does not define the profile's format; only the authority reads the profile and compares its digest, and receivers of frames do not.

### Application key rotation

`host.renew` optionally carries `application_key_rotation`, an object with both `key`
(an application key) and `proof` (an Ed25519 signature). Omitting the object keeps
the application key. The new key needs a key id the installation does not use yet: not
the host's current key id, another host's, or an authority key's (`invalid_body` at
`/body/application_key_rotation/key/key_id`). Its public key is new too: no certificate the
receiver holds has it under another key id (`invalid_body` at
`/body/application_key_rotation/key/public_key`), so a revoked key cannot come back under a
new key id. The one exception is a retry after a lost
reply: the key id of the certificate that already replaced the signing one, with the same
public key, which is what a retry after a lost reply names; the authority answers it with
that certificate. The renewed certificate has a higher membership epoch, like every renewal.

The new private key signs these bytes:

1. Copy the complete renewal frame as received, keeping unknown optional fields.
2. Remove the top-level `signature` and `body_digest`, and remove only `proof`
   from `body.application_key_rotation`. Set `algorithm` to `ed25519`.
3. Prefix its RFC 8785 canonical JSON with the registry's `renew_key_proof_domain`,
   `universal-agents/host-renew-key-proof/v1`, followed by one newline.

The old private key then signs the finished frame, including the new-key proof,
using the normal frame procedure. This order avoids circular signatures and binds
the proof to the issuer, audience, message id, expiry and entire renewal body.
`sign_renew_key_proof` followed by `sign_frame` implements it. A structurally valid
renewal with an invalid new-key proof is refused as `invalid_body`.
`signing-vectors/key-rotation.json` and `examples/valid/host.renew/rotate.json`
provide the exact bytes, proof and finished frame for other implementations.

## State records

Hosts, agents, placements, the team view and the block list are key-value records, not messages. Each value is a signed state document (`schemas/state.schema.json`):
- the record type, the writer's protocol label ("Versions"), its key and its writer;
- a sequence that only grows;
- issue and expiry times;
- the body, its digest and an Ed25519 signature over the domain prefix `universal-agents/state-record/v1` and a newline, followed by the RFC 8785 canonical JSON of the document without its signature.

The registry's `state_records` section names each record's bucket, key form, signer, the roles whose certificates may sign it (`signer_roles`), the roles that may store it (`writers`), its body schema, for records that end how long after it is written a record may end (`max_lifetime_seconds`, "Trust over time"), and for records that readers judge by age how long one counts as fresh (`fresh_seconds`). The trust records of "Who sent it" use the same format and are kept by the trust store (`TrustStore.add`). The records here report state, are used as soon as they are read, like requests, and are verified on every read (`TrustStore.verify(data, record=..., now=..., held=...)`):
- **Writer.** The record is signed by its writer's host certificate, valid when the record was written, not revoked, and with one of the record's `signer_roles`. The reader holds a current revocations record of the writer's installation (`revocations_not_current`), whoever the writer is: only the authority's installation traffic needs none. Only hosts of the reader's own installation write state reports (`wrong_issuer`): agreements carry durable work only, and a peer's host keeps its own state in its own installation.
- **Epochs.** The writer's certificate meets the reader's minimum epochs (`epoch_too_old`).
- **Time.** A record that has expired, or is dated ahead of the reader's clock by more than the clock tolerance, is refused (`expired`, `not_yet_valid`). A record of a bucket with a per-key lifetime (`ttl_seconds`: host liveness, 60 seconds) states an expiry within it (`invalid_body`), so a copy kept elsewhere is never read as current. A report with a longest lifetime (the block list, 7 days) states its expiry, within that lifetime of being written (`invalid_body` at `/expires_at`).
- **Sequence.** The reader passes the sequence and digest of the record it holds for the key, if any. An older sequence, or other content under the same sequence, is refused (`replayed`), so a reader that holds a newer record never reads an older one written back to the bucket. A reader that holds nothing, after a restart for example, takes the newest record it reads: host liveness records expire within a minute, but agent, placement and team-view records do not expire, so a reader that must not go back keeps the highest sequence it has seen across restarts.

A reader refuses a state report with the first failing check, in the registry's order:
1. `too_large`, `malformed` (the document's form, and a record of another type than the one read: `TrustStore.verify` takes the record type its bucket holds);
2. `wrong_issuer` when the writer's type is not the record's signer (it decides where the key comes from), then `unknown_key`;
3. `bad_signature`, `bad_digest`, `revoked`, `revocations_not_current`, `epoch_too_old`;
4. `wrong_issuer` for the writer's roles or installation, then `wrong_team` for the record's team, read from the key or the body as received;
5. `expired`, `not_yet_valid`, `replayed`;
6. `invalid_body`: the body schema, then the record's dates (its expiry, its bucket's lifetime, a trust record's single validity window and its longest lifetime), then its key and body rules.

Trust records (`TrustStore.add`) follow the same order without the reader's checks, except `not_yet_valid` for a record dated ahead of the receiver's clock ("Trust over time"); their own-installation rules need the body and come with its rules. The two-defect examples under `examples/state/invalid/` (`also`) pin the order.

What each record says, and what `TrustStore.verify` checks about it:
- **Host liveness.** A host writes only its own record, under its runtime id. The record names the certificate it is signed with: its id, membership epoch and `sha256`, the SHA-256 of the certificate record's signing bytes, which `TrustStore.add` recorded. It allows at most that certificate's sessions. Its roles, teams and agent types are the certificate's, so the record does not repeat them.
- **Agent records.** The key is `<team>.<agent>` of the body, and the team is one the writer's certificate serves. A reader accepts an agent record only from the host its placement names; the reader checks that, since it needs the placement.
- **Placement.** The key and team follow the same rule. The team services write a placement with compare-and-set on the last key-value revision and the next sequence. The fencing token written into admission records is the signed sequence, not the revision, which the server assigns and nobody signs. `host_epoch` is the membership epoch of the host's certificate when the agent was placed. Renewals raise the epoch without moving the agent: a reader accepts the placement while the host's liveness record names a certificate of that runtime at `host_epoch` or later.
- **Team view.** The key is exactly `<team>.<entry>.<id>`: a team the writer's certificate serves, the body's entry type, and one more token that names the entry (it need not be a task id, which may hold dots). Entries name people only by opaque references and the display names the team's policy allows. An Objective's title is the person's own words, so the team services delete an entry when its item closes and when the person it names departs. A task's entry repeats its holder's custody window ("Custody windows").
- **Block list.** The key is the body's team, one the writer's certificate serves, and only the team services sign it. No block id and no person appears twice. Readers keep the highest sequence they have seen, also across restarts, and `fresh(record, now)` tells whether the list is recent enough for `fresh_check` tools ("Access on remote hosts").

**Not generated yet.** The NATS permissions for the key-value buckets, the object store and reading the dead-letter stream, and deleting a departed person's raw copies there ("Dead letters"), come with the services that use them. Until then the registry's `writers` say who may store each record, its `write_rule` says who reads it where only some hosts may (every host of a team reads the team's block list), and the readers' checks above do not depend on who stored it.

## Dead letters

A receiver that sets a message aside picks a copy id at random (256 bits, written as 64 lowercase hexadecimal characters). It keeps the exact bytes at `dlq.raw.<copy>` under its own runtime id, and sends a `dlq.notice` to its team's services, which tell administrators. Both wait in `UA1_DLQ` for 30 days. The installation authority, whose installation traffic has no team, sends notices about that traffic to a team its certificate serves; a certificate always serves at least one.
- **The notice holds identifiers only:**
  - the copy id, which its subject also names;
  - the reason: a verification refusal code, or `handler_failed`, `delivery_limit` or `upgrade_drain` (the generator checks that the list names every refusal code except the temporary `revocations_not_current`, for which nothing is set aside);
  - the refusal's JSON pointer, up to the last field the receiver's schema knows (`FrameRefused.known_at`): an unknown field is named by the object that holds it, so a name the sender chose never reaches the notice;
  - where the message sat in its stream;
  - the set-aside message's own unverified claims: kind, message id, issuer team and runtime, protocol;
  - the raw copy's size and SHA-256.

  It has no free text, because a refusal's details can quote the content.
- **Raw copies** have no frame kind: they keep the refused bytes exactly, so a person can inspect what arrived. Generated permissions let each notice sender publish copies under its own runtime id only. A receiver keeps a copy only when it is at most `max_frame_bytes`, which with its headers fits the stream's message limit; for a larger message the notice says `raw.stored: false`.
- **People's content.** A raw copy can hold a person's message. Only the team services read `UA1_DLQ`; its read grants come with them. Copies expire with the stream after 30 days. When a person departs, the team services delete the raw copies whose frames name that person, in an authority token or a person reference.
- **Retry keys** name the receiver's runtime and the copy id, so two receivers' notices never share one.

## Versions

Within one protocol label:
- a sender at the same or an older minor is read strictly: an unknown field is a defect;
- a newer minor's unknown optional fields are ignored.

The frame states its minor, so the receiver chooses before reading the body. State records
state theirs the same way (`protocol`), so a certificate or a liveness record can gain
optional fields within the major too; the signature covers the record as received,
unknown fields included. A change that an
older receiver must understand needs a new major, which brings new subjects and streams.
Receivers recompute keys, so a kind's key parts and copies are fixed for the major: a newer
minor never adds, removes or reorders them.

**The contract digest.** The compatibility record (`generated/compatibility.json`) names
the contract in `contract_sha256`: the lowercase hexadecimal SHA-256 over every Markdown,
YAML and JSON file under `contracts/messages/v1/` except `generated/`, this README and the
examples included. Hidden files and folders (a name starting with `.`) and other kinds of
file, such as an editor's backup, are no sources and do not count. The repository's
`.gitattributes` checks the sources out with LF line endings on every system, so a Windows
checkout hashes the same bytes. The
files go in order of their paths relative to that folder, with `/` between folders,
compared as UTF-8 bytes. For each file the digest takes its relative path in UTF-8, a zero
byte, the file's size in bytes as decimal digits, a zero byte, and the file's bytes. While
the label ends in `-pre`, a fix may change the contract without changing the label, so
hosts of one installation refuse a peer whose digest differs from their own. The generated
code names its own digest (`custom_messages.wire.kinds.CONTRACT_SHA256`).
- **Where it travels.** `host.join`, `host.renew` and each host liveness record carry the
  host's `contract_sha256`. Another revision of the contract may shape these bodies
  differently, so the digest is read before the rest of the body: the installation authority
  reads a join's or renewal's `protocol` and `contract_sha256` first, and `TrustStore.verify`
  reads a host record's digest after its signature, writer and times and before its body.
  Otherwise a host of another revision would be refused as malformed and never learn why.
- **The authority.** While the label ends in `-pre`, it answers a join or renewal whose digest
  differs from its own with `protocol_mismatch`, naming the digest it runs
  (`accepted_contract_sha256`) and what to install. It still answers a renewal that only gives
  up agents or pools ("Credentials follow placement"), so a host on another contract can hand
  its agents over. A host upgraded in place renews with a new `renew_id`, since a repeated one
  gets its stored outcome back ("Stored outcomes").
- **Readers of host records.** A host record that names another digest is authentic, so
  `TrustStore.verify` accepts it without reading the rest of its body and marks it
  (`other_contract`, with `their_contract_sha256`). A reader sends that host no new work,
  places no agent on it and logs the host and both digests, but still sends it control
  messages for the tasks it holds (stops, custody, access decisions, the ends of waits). The
  team services keep counting its custody windows from its records, so its tasks never get a
  second holder without a person's override ("Custody windows").
- **The host on another contract.** A host learns that its digest differs from the team
  services' host record, which it reads when it starts and whenever it changes, or from
  `protocol_mismatch`. It then stops pulling from worker pool queues and from its agents'
  inboxes, keeps reading their control queues, finishes the turns in progress and hands back
  (`task.handback`) every task it has not finished, holding every action outside the team
  meanwhile, and renews only to give up its agents and pools. Messages either side can no
  longer read are set aside as dead letters, as usual.

The digest is compared only within one installation: frames from another installation
(`x-<installation>`) carry none, and federation agreements gain it before two installations
connect. A released label (no `-pre`) compares only the label and its minor ("Versions"
above), so the digest is then informational. `--check` regenerates the record, so a changed
source with a stale digest fails it.

## Operation inputs and outcomes

An operation's retry key is made from the parts its registry entry lists ("Idempotency
keys"). Each part points at a required request-body field, a required frame field, or the
audience id its address names (`/audience/id`). It never means a value inferred from an
authority token. `tasks.steer` uses `/body/steer_id`; `staged_changes.apply` gets a new
`request_id` when the person confirms again after `agreement_required`, so the new command
has a new key. Retrying the same command keeps its key. The exporter rejects parts that are missing or optional.

An operation that takes a token states its `authority_binding` ("On behalf of a person").
A gateway's command carries its own id, `request_id` (`steer_id` for `tasks.steer`): the
gateway makes a new one for each new command and keeps it when it retries the same command,
and the command's token is bound to it. Reads carry one too, so their token is bound to
them; their retry key stays the message id. An agent's operation carries its root task's
token. An operation both may send lists both bindings, each with the roles that present it.

**Relays to an agent's host.** The holder answers for its own queue through the team
services. The gateway sends `tasks.list`, `tasks.list_finished`,
`tasks.remove` and `tasks.purge` to the team services (`svc.team`), and only the team
services pass them on to the agent's host (`ctl.agent.<agent>`, `senders_by_address`); the
agent's host refuses them straight from the gateway as `wrong_sender`. `debug.dump` takes
the same way to `ctl.agent.<agent>`: today the lead applies it in its own process, and
the relay lets the team services move to another host without a new message. A
relayed frame carries the gateway's command token unchanged, with the
same `request_id`. The agent's host verifies the person from the gateway's signature: no
body names a person, and the team services never sign tokens. Command tokens are accepted
only from these senders, so an agent host cannot use one on another operation.

### Knowledge

These operations keep the knowledge service's current behavior. Their common page,
contribution and review-flag shapes live in `knowledge.read.reply.schema.json` so
every knowledge reply carries the same fields without changing the shared frame.

`knowledge.list` accepts `all`, `team` or `personal`, a query, and optional
`page_type` and `tag` filters. `all` includes the verified person's own pages and
the team's pages; work for nobody sees only team pages. Gateway browsing keeps
`KnowledgeService.browse`, including active or archived pages, a matching total
and the browser's 20-row pages. Agent searches keep `KnowledgeService.search`,
which searches active pages with the type and tag filters and caps each page
at `search.max_results`, at most 50. Adapters pass `offset` through to search;
the cap never limits the complete result set. Agent replies omit `total`
because search does not count all filtered matches. After selecting rows that
fit the frame, adapters check for one more result at `offset + returned` using
the same search filters. If it exists, `next_offset` names that position;
otherwise continuation is absent. This preserves paging beyond the first
configured page without scanning the whole result set for a count.
Gateway browsing requires its exact matching `total` and does not send the
agent-only type and tag filters. Senders lowercase page types and normalize tags
as the service does. The types are `concept`, `how-to`, `decision`, `lesson`,
`reference` and `source`; tags have up to 80 characters, with at most 100 per page.

List rows include the type, summary, tags, status, decimal `seen_version`, update
time and optional search snippet. Snippets use inline-or-blob text because the
store's word-based search snippets have no character bound. All list replies
respect the serialized frame limit even when fewer rows than `limit` fit.
`next_offset` is present only when more rows remain and advances by the number
actually returned. History pages slice the service's latest 50 revisions; their
`total` counts that window, preserving today's bounded history. Contribution
lists page through all the person's pending proposals with their matching total.
They accept up to 100 entries for agent lists; gateway browsing keeps its current
50-entry service cap and 20-row browser pages.

A detailed page also carries its content, creation time, current editor,
`frozen_until` when frozen, backlinks, resolved links, up to five oldest open
notes, and up to 20 pending proposals with their ids, kinds and creation times.
The gateway uses the proposal list's length for its pending count. Backlinks keep
the service's 20-row bound and links its 100-row bound. Each link gives the text
as written, destination space and page, and whether it exists. `redirected_from`
records the merged name that was followed. When reading an earlier revision,
`seen_version` still names the current page revision, while `shown_revision` and
`shown_by` identify the revision shown and its editor. The shown title, type,
summary, tags and content come from that revision. History rows carry each
revision's title, status, change kind, change summary, creation time and editor.
The gateway keeps today's editor-name rewrite before sending records to the
browser; person references are never browser display names.

Every detailed page uses `type: inline` with those fields, or `type: blob`
with an `application/json` reference to the complete inline page. This applies
to reads, mutation replies and the current page inside a contribution.
The receiver validates retrieved JSON against the inline page schema before
using it. A page's backlinks alone can exceed the frame limit under supported
settings, so moving only its content to a blob is insufficient. Senders move
the complete page to a blob when the signed reply would otherwise exceed
262,144 bytes. The file keeps all metadata and service-bounded collections.

Writes have one optional `content` field, either `type: inline` with `text`, or
`type: blob` with an object-store `ref` to UTF-8 plain text. The two forms cannot
be mixed. Page and contribution replies use the same field. An edit may omit
title, content, type, summary or tags to keep those values; an empty summary or
tag list clears that field. A create without a title or content is refused by
the service. Without `seen_version`, a write creates a page and refuses an
existing name; with it, the write edits that decimal revision. The default type
for a new page is `reference`.

Merges carry the source's `seen_version`, the destination's `target_seen_version`,
and the merged `content`. Both versions must still match before either page
changes. Agents working for a person merge only that person's personal pages;
team merges run in the curator's team maintenance work. An omitted merge title
or summary keeps the destination's value; an empty summary clears it.
`confirm_review` records confirmation of flagged
content and grants no access. Archive and revert carry a nonempty `reason`.
For a person's Web Chat action, the gateway sends the fixed text
`Archived on the Web Chat Knowledge page` or `Reverted on the Web Chat Knowledge page`;
the browser never supplies this text. Agents supply their own reasons. Senders
truncate archive and revert reasons and change summaries to the configured
`max_summary_chars`, at most 4,000, as the service does today.

An agent working for a person proposes team notes and archives. These operations
return `pending_review` and a `contribution_id`, as `knowledge.write` does. This
outcome means a proposal was saved; it does not mean the page changed. The reply
also offers the proposal kind, page reference and review flags for the agent's
current result display.

Contribution list, read, withdrawal and rejection results retain the proposal's
kind, type, summary, tags, change summary, base revision, state, creation time,
author and review flags. A full read includes its content and the current team
page for comparison when that page exists. A proposal has no independent
`seen_version`. Publishing may omit `seen_version` to use the proposal's base
revision; a proposed new page under a free name creates at revision zero.
An explicit revision checks the page the reviewer compared. `edited: false`
publishes as proposed. `edited: true` sends edited page fields or an edited
inline-or-blob `note`. A `page` override is allowed only for a new-page proposal;
otherwise the reviewed title supplies the new name, never an unreviewed proposed
name. An archive publishes status only and refuses edited page fields.
Successful publishing returns the page and, for a note proposal, the added note.

Notes in requests and replies use inline-or-blob text. The receiver enforces
`max_note_chars`, up to 50,000, and `max_body_chars`, up to 500,000, after fetching
the text. Senders use blobs when a field exceeds the 32,768-character inline
limit or when all the inline content together would exceed the frame budget.
Each returned note has its server-assigned id, content, creation time and editor.
Resolving a note needs only its `note_id` and `merged`, true after incorporating
it or false to dismiss it; page and space are optional context. Reading again
exposes the next notes. Freeze, unfreeze, resolve and reject carry no
`seen_version` and offer no store-conflict refusals, because the runtime never
checks a page revision for them. Freeze takes `minutes` from one minute to one
week; senders clamp a larger duration to one week as the service does. Its reply
includes the freeze expiry; an unfreeze reply omits it.

Review flags are objects with kind, label, field, line and column, never matched
private text. An empty field and zero positions mean no known location. Kind is
bounded text, rather than an identifier pattern, to retain `custom:<name>` with
any configured pattern name of up to 60 characters. The contract allows 67
characters for kind and 240 for label. The runtime sets no upper bound on flag
counts or rejection reasons; this contract chooses at most 100 flags per result
and 32,768 characters for a rejection reason. Deployments must keep reports and
rejection text within those bounds when using these messages. A rejection needs
a nonempty reason. Personal reads without a verified person return
`personal_space_unavailable`; withdrawal retains `feature_off` when knowledge
is disabled.

Contract verification pairs schema/model round trips with real SQLite knowledge
workflows, including stale source and destination versions, pending proposals,
note discovery and resolution, archive and revert reasons, and freeze duration.
The protocol adapters are not live yet; these checks do not prove NATS delivery
or object-store integration.

### Memory and staged changes

`memory.*` operations act on the team's `coremem` or the verified person's
`usermem`. A fact's `seen_version` is its record digest, including its internal
identity and last change time. Reusing a deleted fact's number does not reuse
its version. Agents must send the version for replace and delete; people's
commands may omit it, as today's numbered memory commands do.

`memory.create` needs `fact_text`; omitted tags and metadata start empty.
`memory.replace` changes only the fields supplied. It needs at least one of
`fact_text`, `tags`, `metadata_json`, `valid_from`, `expires` or `clear_expiry`.
An empty tags array or metadata object clears that field. `clear_expiry: true`
maps to today's `invalid_after_utc="never"`; sending it with `expires` is an
`invalid_request`. Omitted fields keep their stored values.

`fact_text` uses `text_content`, either inline text or a UTF-8 plain-text blob.
Today's service has no fact-text length limit, so a blob preserves long facts
without exceeding the frame limit. `metadata_json` encodes an object as JSON
text, at most 16,384 characters. Public replies exclude the reserved
`imported_from` metadata, as today's public memory view does. For protocol 1,
each bank's `max_tags` setting must stay within 100, `max_tag_chars` within 256,
and `max_metadata_chars` within 16,384. Today's settings have no upper bounds;
these larger-than-default bounds leave room for metadata and tags in one
frame when fact text uses a blob. The receiver still enforces the bank's
configured limits. This contract does not change runtime settings.

`memory.list` takes a zero-based `offset` and a `limit` from 1 to 100. The
adapter maps them to today's one-based start and end rows. `memory_id` sorts
by number ascending; `newest` by update time and then number descending;
`valid_from` by start time and then number ascending; `expires` by expiry and
then number ascending, with no expiry last. The last two map to today's
`valid_from_utc` and `invalid_after_utc` sorts. The reply gives `total` and,
only while more remain, `next_offset`. It returns fewer rows than requested
when needed to fit the frame, using blob text even for a single large fact.
`memory.show` returns one fact. Create, replace and delete return an event id;
`memory.undo` reverses a create, replace, delete or expiry while that event's
result is still current. Undoing a create deletes the fact and returns no
fact; the other undo results return the restored fact. Only create checks
bank capacity, so replace, delete and undo do not offer `capacity_reached`.
The gateway renders today's memory command text from the request and typed
reply, using `render_pinned_memory_result`'s formatting and the person's time
zone. The service does not send a second rendered copy.

Topic search reports the conversation's stored status. New threads are `active`;
after a turn completes, the store records that task's progress state. A thread
status therefore allows `active` as well as the task states, without adding it to
the task-state definition.

`staged_changes.apply.seen_version` is the staged `plan_digest` returned by
the staging tool. A changed digest gives `changed_since_read` with the current
digest. Approval still applies only to that exact plan. `confirmed` records
conversational agreement when authorization is off; it grants no approval
when authorization is on. After `agreement_required`, a newly confirmed
command has a new request id because its body changed.

Successful application returns `state: applied`, the recorded `approval`,
the person's optional decision `note`, and the adapter's `result_json`.
Approval keeps today's mode, approver and approval time; only
`person_approval` may name an `access_request_id`. The four modes are
`person_approval`, `held_access`, `agreement` and `operator_configuration`.
Notes keep today's 2,000-character limit. Agreement replies keep titles up
to 400 characters and 1 to 40 effect lines of at most 1,000 characters each.
Adapter results are free objects today; `result_json` encodes the object in
at most 16,384 characters. Adapters must keep their result within this bound.
A `failed` outcome preserves the approval, note and adapter error result as
a final receipt, rather than treating it as a retryable `runtime_error`.

`denied` and `withdrawn` name the access request and keep the person's note.
`refused` preserves the reason and note when the plan can no longer apply,
including after approval. Its reason is bounded to 16,384 characters because
today's exception text has no limit. `waiting` names the access request and
is never stored as a final outcome. Retry the same request id after its
decision so the approved call can continue. Shared covered-change refusals
remain available for the later request-conflict checks.

### Objectives and heartbeat items

These operations preserve the 0.9.8 Objective tools and the person's controls.
The gateway uses a command token bound to `request_id`. Lead operations use
the current root task's token. The receiver resolves the person from that
token and checks named tasks and Objectives with the existing ownership
service. A task id supplies context, never authority. Session and checkpoint
calls name the active task and its actual session. Inaccessible records are
reported as missing.

`objectives.list` accepts the gateway and lead. The gateway sees the person's
Objectives, including closed ones by default. The lead sees team Objectives
and those of the person its task works for, excluding closed ones by default.
Optional `statuses`, `horizons` and `include_closed` preserve the tool's
filters. `offset` and `limit` page the results, with `limit` from 1 to 100.
The reply's `total` counts matching records and `next_offset` appears only
while more remain. The gateway's existing discovery limit stays 100 records;
paging retrieves that listing without requiring one large frame. Lead reads
keep the store's newest-first order. Receivers may return fewer than `limit`
to fit the frame; callers continue with `next_offset` until it is absent.

Each row preserves current focus, plan id and summary, subgoals with status
and result, criteria with evidence and update time, linked ids, work-policy
status, and update and deletion timestamps. `objectives.get` resolves an
Objective by its id, task, plan, or current verified task context. It returns
the full record and rendered Markdown, as today's tool does. A large record
uses `objective.type: blob` with an `application/json` reference to the same
complete record. A list row's `details_file` similarly carries its full
summary when nested collections cannot fit. No text or list is truncated.

Stored Objective owners use `durable_owner_id`, including the runtime's
`manager_scope:<team>:<role>` values. They may contain colons and exceed the
128-character record-id bound, so they have a separate 16,384-character
bound. These reply fields convey stored data. Ownership checks still resolve
the caller from verified identity; routing and certificate agent ids keep
their subject-safe type.

There are two Objective versions. A list row's `seen_version` is
`contract_sha256(objective.model_dump(mode="json"))`, from
`manager_control_runtime._runtime_objective_summary`. The gateway sends it
on `pause`, `resume`, `stop`, `abandon` and `delete`; these controls check the
whole record, including progress, status and events. The row's
`objective_version`, and `objectives.get` and lead-write replies' `seen_version`,
come from `custom_messages.records.objectives.objective_version`.
Lead `update_progress` and `update_status` send that digest as `seen_version`.
It covers decision fields and criteria without criterion timestamps.
Runtime bookkeeping, including status, focus, progress, owners, links and
events, is excluded so running work does not invalidate an agent's edit.
`changed_since_read.current_version` uses the digest checked by its operation.
Both digests are 64-character lowercase hexadecimal strings.

`objectives.create` requires `why`, title and desired outcome. It also carries
completion policy, criteria, constraints, non-goals, required
user confirmation, focus, progress, and `creation_mode` of `promote_task` or
`spawn_task`. An optional `task_id` selects a source task working for the same
person; otherwise the current verified task supplies it. The reply returns
the Objective version, root task and plan, creation mode and lineage ids.
Creation ensures an Objective-owned task and plan as today.
Each `success_criteria` item is existing inline-or-blob description text or a
`type: criterion` object. The object needs `description` as `text_content` and
may supply `criterion_id`, `status`, `evidence_summary` as `text_content`, and
`updated_at`. The adapter removes the wire-only `type`, resolves text, and
passes the remaining object to `ObjectiveSuccessCriterion`, through today's
`create_objective.success_criteria_json`. Supplied ids, evidence, statuses
and timestamps survive creation. Omitted fields keep today's generated id,
`open` status, absent evidence and current update time. A description-only
item keeps those same defaults. Timestamps use the protocol's UTC spelling.
The `type` discriminator keeps text and structured criteria distinct for
portable code generation.
Lead-write replies may include the complete saved record as an `objective`
JSON file reference and its rendered Markdown, keeping the acknowledgement small.

`update_progress` can change progress, focus, criteria, or any combination.
At least one must be present. Criterion updates name an existing criterion
or describe a new one, with optional status and evidence. As today, the store
creates a criterion from a description when its id does not resolve; an
update with neither a known id nor description changes no criterion.
`task_id`, `plan_id` and `user_visible` retain the tool's event context.
`update_status` carries `summary`, `user_confirmation_summary`,
`satisfied_by_current_task` and the same event context. The receiver answers
`confirmation_required` when satisfaction requires the person's recorded
confirmation text. Deletion stays with the person's controls. `incomplete`
and `skipped` identify lifecycle steps that failed or protected links left
unchanged, as today's warnings do. After a person control the gateway can
refresh with `objectives.list` and `tasks.inventory`; the control reply does
not embed a refreshed inventory.

The remaining covered tools have explicit operations:

- `objectives.work_sessions.enable` takes the Objective, active task,
  confirmation summary, optional profile name and `confirmed` flag.
  `disable` takes the Objective, task and confirmation flag; its protected
  schedule remains an inert record. `start` opens one work window on the
  active Objective-linked task. All three require the direct person request
  as today's tools do, and return the saved policy or session.
- `objectives.work_profiles.apply` carries the exact proposal id and digest,
  active task, confirmation summary and flag. Its result distinguishes an
  Objective policy, reusable installed profile and already-applied proposal.
  The coordinator checks the proposal's digest and expiry. This digest is
  separate from an Objective version.
- `objectives.work_profiles.propose` persists an inert proposal through
  `propose_objective_work_profile`. It carries the active `task_id`, normalized
  `profile_name`, `rationale`, and a complete `profile` containing cadence
  and budget. The adapter passes that profile's fields to today's flat tool
  arguments. Omitted cadence time zone means `owner`; omitted `scope` means
  `objective`; omitted `replace_existing` means false. `objective_id` selects
  an owned active Objective or defaults to the current task's Objective.
  Reusable proposals have no Objective target. The operator's cadence,
  budget, name-replacement and installed-profile limits still apply. The
  reply returns the persisted proposal, its exact digest and expiry.
- `objectives.work_profiles.list` maps to `objective_work_profiles(action="list")`.
  It needs no direct person request or confirmation. `include_proposals`
  defaults to true. Its `catalog` retains configured profiles, this person's
  active installed profiles, the default name, all custom-profile limits,
  and the latest 50 proposals when requested. Configured entries and installed
  records retain `profile_source` to distinguish them. Installed entries
  retain their ids, acceptance provenance and proposal digest.
  The installed-profile limit stays 1 to 500. Configured profiles have no
  runtime count limit; protocol 1 chooses at most 1,000 configured profiles,
  allowing at most 1,500 entries together. Deployments must keep within that
  bound when switching to the protocol.
- `objectives.work_profiles.remove` maps to `objective_work_profiles(action="remove")`.
  It carries `profile_name`, active `task_id`, `confirmation_summary` and
  `confirmed`. It returns the complete removed installed-profile record,
  including removal time, task and summary. The person must explicitly
  confirm removal in a direct request. Existing Objective policy snapshots
  retain their copied profile. Proposal creation also requires a direct
  person request, but does not require confirmation and never applies a
  proposal. Apply still checks confirmation, digest, expiry, replacement
  state and policy state before changing anything.
- `objectives.work_sessions.status` maps to `objective_work_sessions(action="status")`.
  Optional `objective_id` selects an owned Objective; an omitted selector
  uses the current verified task context. Its `snapshot` retains the policy,
  latest 20 sessions, and the configured checkpoint history, from 1 to 500
  entries. These are the runtime's current windows, not a complete archive.
  A missing policy is omitted, an empty history stays an empty array, and
  a disabled coordinator returns an empty snapshot, as today's tool does.
  `tuning_signals_json` contains the runtime's observation object as JSON text,
  up to 16,384 characters, preserving fractional averages and ratios and
  null values without putting fractional numbers in the signed frame.
  It is omitted when the runtime returns no tuning signals. Those observations
  grant no access and do not change budget limits.
- `objectives.record_checkpoint` carries the active task and session,
  observe, orient, decide and act text, health, evidence changes, completed
  subgoals, next subgoal, blockers, effects in progress and artifacts. It
  returns the saved checkpoint. Session `active_seconds_used` becomes
  integer `active_ms_used`, rounding reported duration down to whole milliseconds.
  Integer budget seconds retain their names and units.
- `objectives.start_task` carries the Objective, source task, work brief,
  optional focus and visibility. It returns the queued task and current plan
  when one exists. `objectives.activate_plan` carries the active task,
  semantic steps of title, objective and optional rationale, and `final_review`.
  The runtime creates internal ids. Its reply tells the caller to return
  control for execution in fresh contexts. As today, the plan builder compacts
  step titles to 180 characters and objectives and rationales to 1,000.
  `final_review` adds the final review step unless one already has that title;
  the reply's `step_count` includes it.

Session enable, disable and start, profile apply, checkpoint, task and plan calls are covered Objective
changes with `seen_version: none`: today's tools take no Objective expected
version. Profile application retains its own proposal-digest check. Current
confirmation, enabled-feature, required-skill and ownership checks still
apply. Covered refusals carry their shared data; `record_busy` and
`runtime_error` remain retry outcomes. Conversational confirmation grants no
access and does not bypass system-schedule approval.
Failures after saving a change remain `ok` with `warnings`, as today's
`after_saved_change` reports them. They must not become retryable failures.

The new profile and status operations are lead-only requests to the team
services, signed for the current root task. `request_id` identifies every
call; reads keep the message-id retry key and propose/remove use the request
id. The task id must be the active task of that signed request. No body may
choose a person. Catalog access follows `fn:objectives`: propose is
`propose_objective_work_profile` at `write`; list is `objective_work_profiles`
action `list` at `read`; remove is action `remove` at `full`; status is
`objective_work_sessions` action `status` at `read`. Propose and remove have
no covered record kind, as the catalog specifies, so they do not acquire
Objective version checks or the five covered-change refusals. Reads have no
covered change either. Their exact refusal lists are in the registry and
reply schemas; `runtime_error` is retryable and the other outcomes are final.

Proposal and removal replies use inline-or-blob records. Catalog and status
replies use a whole `catalog` or `snapshot` with the same alternative. Every
record blob is UTF-8 `application/json` containing exactly the inline
`value`, validated against its value schema after retrieval. The catalog
schema is `objectives.work_profiles.list.reply.schema.json#/$defs/profile_catalog`;
the snapshot schema is
`objectives.work_sessions.status.reply.schema.json#/$defs/work_session_snapshot`.
Proposal files use `pending_profile_proposal` in the propose reply, with no
application fields because creating a proposal applies nothing. Removal
files use `removed_installed_profile` in the remove reply, including all
removal provenance. Record mappings omit runtime `message_class` markers
and rename `owner_canonical_user_id` to `owner_person`; the value still comes
from verified identity. Files retain all nested fields and collections,
with the same text references and timestamp/unit mappings as inline records.
Files allow large
histories within current record-count bounds without truncation or an
oversized frame. Tuning JSON must encode an object within its stated bound.
Pure suggestions and inert profile export rendering remain local. SQLite
conformance checks exercise today's tools and stored records; future
dispatch and blob retrieval are not implemented or live-tested here.

`heartbeat_items.list` is a lead read with `source_id`, `include_disabled`,
`offset` and `limit`. It returns source and launcher diagnostics, full item
records and versions, `total` and optional `next_offset`. The default includes
disabled items. When the source is absent, a successful inspection reports
`missing_source`, or `disabled` when heartbeat is off, with no items. An existing
source returns its items even when heartbeat is disabled, as today's tool does.
Source ids remain free configured strings, bounded at 16,384 characters.
Item versions come from `storage.heartbeat_repository.heartbeat_item_version`:
id, title, instruction, target agent type and Objective, excluding run times.
Add can select the source. Changes, removal, enable and disable send the
item's `seen_version`. A saved item can still report heartbeat-disabled or
launcher-missing warnings; callers must not retry that as a failed create.
Both create operations are covered with `seen_version: none`.

The runtime has no upper bounds on much Objective prose or these nested
collections. Protocol 1 uses `text_content` for prose and files for larger
records. Display names and other free strings allow 16,384 characters where
no stricter shared id type applies. Stored Objective, policy, session and
checkpoint collections have no artificial item-count ceiling, whether inline
or in the complete record, summary or snapshot JSON file. This keeps existing
large collections readable. Senders use the serialized frame size to choose
the file representation, and receivers validate the complete retrieved value
against the same typed schema. Actual service history windows, including the
latest 20 sessions and configured checkpoint history, still apply.
Free event details become `details_json`, bounded at 16,384 characters.
Inline request collections keep their 1,000-item bound where specified. For
requests without a file alternative, code that moves a tool onto these operations must
keep its inputs within these bounds.
These bounds change what the adapter accepts; they do
not authorize truncation. Senders count serialized UTF-8 bytes and move
content to files or shorten a page before the frame reaches 262,144 bytes.
Local definitions keep these records typed without changing shared schemas.

### Schedules

`schedules.*` operations keep the stored schedule, run-note and worker behavior of
`custom_messages.contracts.schedule_v1`, `schedule_changes`, `schedule_worker_service`
and `schedule_worker_inspection`. The team services check ownership through the verified
task context or command token. A schedule's name and assigned agent type may be absent.
The page then displays its id or an unspecified assignment, as today.

A schedule's action says what each run does: `task` gives its instruction to a model turn, and
`fixed_message` sends its text as it is, without a model turn, so a plain reminder needs no
model. `schedules.install` sets it (`action`). `schedules.list` rows and the `schedules.get`
reply carry its type (`action.type`, with the same values), so the person's schedule views can
mark the schedules that run without a model, and `schedules.update` switches it. Today's
runtime runs every schedule as a model turn, so its schedules read as `task`.

`schedules.list` pages the schedules the caller may see. Each row returns the schedule's
listing digest as `seen_version`, action type, timing, repeat limit, run notes and worker
assignment; `instruction_preview` shows the start of the instruction or of the fixed message.
The assignment keeps `automatic_creation` as `not_configured`, `enabled`, `disabled` or
`default_policy`, plus `review_agent_type`, `upgrade_required`, `desired_agent_type` and
`reassignment_pending`. `not_running_since` and `not_running_explanation` explain a stuck
schedule. Automatic creation says whether startup is allowed; it does not prove that a
worker started or has access. The reply's `next_offset` appears only when more rows remain.

`schedules.get` reads one exact `schedule_id`. It maps the existing
`list_scheduled_jobs(schedule_id=...)` detail read to `fn:schedule_runs`, action
`list_scheduled_jobs`, level `read`. It is not a new runtime tool. Gateway reads use
a command token bound to `request_id`; lead and worker reads use root-task authority.
The receiver checks the same owner scope before reading details. System work may read
only the schedule named by its signed context. A missing or invisible schedule returns
`not_found`; a refused scope returns `not_allowed`. An offset beyond the text or another
invalid selection returns `invalid_request`; an unsuccessful read returns `runtime_error`.
This read has no covered change, stores no outcome and uses `/message_id` as its key.

The request's `offset` and `max_chars` map to `details_offset` and `details_max_chars`.
The wire accepts 1..4,000 characters per page, the runtime's existing excerpt limit.
The reply's `detail` keeps `text`, `offset`, `total_chars`, `sha256` and, only when more
text remains, `next_offset`. Every page also carries the schedule's `action.type`, outside
the detail text. An offset at the end returns an empty final page. Offsets
and lengths count Unicode characters, not UTF-8 bytes, and allow 0..2^53 - 1. The
receiver serializes the complete safe projection with `ensure_ascii=False` and sorted
keys before paging. `sha256` is the lowercase hexadecimal SHA-256 of that complete
UTF-8 text. Callers assemble pages only while it stays unchanged; if it changes, start
again at zero. `seen_version` alone cannot detect changes to the run ledger because
the listing digest deliberately leaves those changes out.

The JSON detail projection keeps these existing `schedule_payload` fields, with their
current names and values, including nulls inside this JSON text:
`schedule_id`, `record_digest`, `schedule_name`, `management_class`,
`system_schedule_kind`, `assigned_agent_type`, `enabled`, `paused_until`,
`expires_at_utc`, `next_fire_at`, `interval_ms`, `cron_expression`, `cron_timezone`,
`repeat_count`, `remaining_runs`, `final_run_in_progress`, `objective_id`,
`owner_canonical_user_id`, `problem_statement` and `schedule_memory`.
`remaining_runs` is null when the schedule has no run limit. `final_run_in_progress`
is true while the last run of a one-time or counted schedule still works; such a
schedule will not run again, and its past `next_fire_at` is that run's, not a missed
one. `problem_statement` and `schedule_memory` retain the full instruction and all
saved policy, state, schema hints, timestamps and ledger entries, including saved
results and notification history. These flexible JSON records have no fixed total size limit in
the runtime, so detail paging avoids imposing the 16,384-character bound of a single
JSON field or silently shortening history. The projection is an explicit allowlist;
new runtime fields need review before they can leave this read.

The adapter must omit `gateway_context` before serialization and hashing. It must
never serialize gateway channel addresses, session keys, account ids, headers or
task-context tokens into these detail pages. The reply may instead carry the existing
opaque `delivery_ref` and `conversation_id` when available. Only the gateway resolves
the delivery reference. Ownership checks happen before that reference is issued.

`schedules.install` keeps create, replace, ensure and refresh. An omitted `worker` lets
the team services fill the lead's type and id, as the runtime does today. A worker object
may name a type, an exact agent, or both; an empty object also uses that default. The
receiver still checks the installation mode, provenance and system-schedule permit.
The `management_class` alternatives forbid `system_schedule_kind` on a user schedule.
A system schedule may omit its kind and then means `unclassified`, as today. The list
uses the same alternatives. A failed write can return `runtime_error` and is retried
without a stored outcome.

Timing is an interval in milliseconds, a cron expression and IANA time zone, or a
one-time date. Cron text accepts shorthands such as `@daily` and `@hourly`, and `#`
expressions such as `0 9 * * 1#2`. The receiver validates the text with croniter and the
zone with ZoneInfo; a character pattern cannot replace those checks. `repeat_count: 0`
means no repeat limit; a one-time schedule still runs once. Interval milliseconds range
from 1 through 2^53 - 1 and repeat counts from 0 through 2^53 - 1. The adapter preserves
the existing tool's whole-second interval conversion and validates that the resulting
date can be represented. These integer bounds replace the old one-year and 100,000-run
caps without changing normal schedules.

Run notes keep `schedule_kind`, `policy`, `state` and `domain_schema_hint_json`.
`policy.notify` is `on_change`, `always` or `never`; `notify_on_failure` is a boolean and
`evidence_required` is task-defined text. `policy.custom_json`, `state.domain_json` and
`domain_schema_hint_json` hold the runtime's free JSON objects. The receiver parses them
as objects. State keeps `summary`, `confidence`, `last_observed_at` and `last_changed_at`.
Confidence is a string label in 0.9.8, for example `high` or `unknown`, so it stays text.
Omitted fields use the runtime defaults on install. The execution ledger remains
runtime-owned; a policy edit must not replace state or ledger entries a run just wrote.

`schedules.update` accepts a partial edit. `action.type` switches what each run does and
keeps the stored text: a fixed message's text becomes the model's instruction, or an
instruction becomes the message sent as it is. `instruction` replaces that text for either
type. The listing digest covers the action type, so a switch changes `seen_version` like any
other edit. `clear_name` clears the optional name;
`clear_expires_at` clears expiration. `time_zone` alone changes an existing cron
schedule's zone, and `next_fire_at` explicitly moves its next run. `enabled`,
`paused_until` and `clear_pause` keep the update tool's combined edits; the separate
pause, resume and disable operations remain available too. `run_notes` patches only its
supplied fields. Top-level `schedule_kind`, `notify`, `evidence_required` and
`notify_on_failure` keep the existing tool's policy-only edits. `schedule_memory_json`
replaces the full stored notes, including a supplied ledger, while `clear_run_notes`
clears them. Omitted update fields leave the stored values unchanged. Clear flags win
over values where today's tool does so, including the name; supplying both an expiration
and its clear flag, both a pause and its clear flag, or both replacement notes and
`clear_run_notes` returns `invalid_request` with a reason. A run-note patch together with
`schedule_memory_json` or `clear_run_notes`, or a top-level policy field also supplied
inside the patch, is refused as ambiguous. The receiver also returns `invalid_request`
for incompatible stored timing, a bad cron expression or time zone, and invalid repeat
limits for a one-time schedule.

Successful install, update, pause, resume, disable, remove and worker configuration
replies may carry `warnings` as `text_content`. Join every runtime `warnings` entry
and any `manager_report.warning` with a newline, in their original order. Preserve
the complete text and its recovery instruction. Use a blob when inline text would
exceed its bound or the frame budget; never shorten or drop warnings. A saved change
stays `outcome: ok` when history, reporting, scheduler wake, cleanup or a post-save read
fails. Store that successful outcome with its effects. It is not `runtime_error` and
must not invite a second mutation.

For a surviving schedule, these successes return `version.state: available` with
`version.seen_version`, the listing digest read after saving. Copy that digest into a
later change's request `seen_version`. If the save is known to have succeeded but the
saved record cannot be read, return `version.state: unavailable`, without a digest,
and preserve the warning. Do not substitute the input digest or invent one. The caller
must inspect before changing the schedule again. Install's `timing_revision` is omitted
when no saved snapshot is available. An update whose runtime result has
`removed_by_expiration: true` returns `version.state: removed_by_expiration`, with no
digest because there is no current record. This separate state prevents confusing a
confirmed deletion with a failed read. A transient digest captured before expiry cleanup
is not a current version and is not returned. Removal replies
use `state: removed` without a version; the request already identified the record being
removed. Expiry removal and explicit removal both remain successful outcomes.

`schedules.set_worker` saves `target_agent_type`, startup `policy`, capability
requirements, `activate_schedule` and `convert_exact_target`. It clears an exact agent
target only with explicit conversion. Omitted policy or capabilities keep the saved
ones; an empty object resets that part to runtime defaults. Policy retains `enabled`,
`profile_id: local`, `expires_at_utc` and typed rules. Fractional runtime seconds become
integer `*_ms` fields: claim wait and interrupted-run skip window allow 0..86,400,000;
startup and admission timeouts 1..3,600,000; retry backoff 1..300,000; optional idle TTL
1..86,400,000. `max_launch_attempts_per_occurrence` stays 1..10 and `launch_when_busy`
stays boolean. Millisecond precision is the wire limit; the adapter rejects submillisecond
values rather than rounding them silently. The operator's tighter limits still apply.

Worker configuration checks both versions before saving, in the same write transaction.
`seen_version` checks the schedule's listing digest; `seen_policy_revision` separately
checks the worker policy's integer revision, with 0 for the first policy. A stale schedule
returns `changed_since_read` with `current_version`; a stale policy returns
`schedule_worker_policy_revision_conflict` with `current_policy_revision`. If both changed,
the schedule check comes first. The success reply returns the schedule version result and
policy revision, `pending_current_claim`, enabled flags, saved policy and requirements,
readiness, missing access and a summary. A current claim finishes before reassignment.
Activation keeps a known-blocked draft disabled. A protected change returns
`approval_required` with its `change_id` for `apply_change`, as today.

The worker service's other refusals use `invalid_request.reason`, preserving the exact
code: `exact_target_requires_explicit_conversion`,
`local_workers_require_supported_root_schedule`, `schedule_requires_canonical_owner`,
`worker_policy_already_expired` or the system timer's `<family>_requires_<type>` code.
Access and owner-scope refusals remain `not_allowed` and missing schedules `not_found`.

Three operations keep the existing worker tools available to remote hosts:

- `schedules.inspect_worker` keeps `inspect_scheduled_worker`. The lead names a schedule;
  a worker may omit the id and sees only the schedule in its current persisted custody.
  It returns the schedule digest and policy revision, registration and eligibility,
  requested, inherited and effective rules, readiness, observed requirements, launch and
  occurrence diagnostics, definition changes and repair instructions. Unsupported system
  or child timers report `worker_configuration_supported: false` with `execution_json`;
  absent diagnostics are omitted rather than null. Suggested refreshes name the current
  policy revision. Dynamic inspection dictionaries use `*_json`; launch and admission
  durations use `spawn_to_ready_ms` and `due_to_admission_ms`.
- `schedules.prepare_access` keeps `prepare_scheduled_job_access`. An optional target type
  and capability requirements preview readiness without saving them. Omission uses the
  saved values. Readiness keeps `ready`, `provisional` or `blocked`, each check's
  `ready`, `deferred` or `blocked` status, reason, required flag and missing holders.
  Capabilities keep up to 64 requirements, each with `capability_id`, `operation`,
  `necessity: required|conditional`, `resource_constraints_json` and
  `source: declared|observed|approved`, plus `runtime_discovery`.
- `schedules.authorize_access` keeps `authorize_scheduled_job_access`. The lead supplies
  the saved `seen_policy_revision`; a stale policy returns the same revision refusal as
  configuration. It gives only access the lead may hand on, ends obsolete setup grants,
  and returns `given`, `waiting`, `ask_a_person`, `ended` and `next_step` under
  `access.status: reviewed`. With authorization off, `access.status: not_needed` says
  why no grant is needed. Waiting reviews do not grant access or start a worker. Access
  approved in a run remains attached to that schedule. This is an access change, not a
  covered schedule write, matching the catalog's `record_kind: none`.

The new reads use `/message_id` as their retry key; authorization uses `/body/request_id`
and stores its final outcome with its effects. All three use root-task authority and
the same team-service routing as the other agent operations. Schedule controls keep their
required `seen_version`; the operator command line must list first too.

Names, schedule kinds, evidence text, confidence labels and JSON text have a generous
16,384-character wire bound because the runtime supplies no upper bound. Cron text is
bounded at 4,096 characters. Each diagnostic reason is bounded at 4,096; readiness and
missing-access lists at 64; eligibility types and ended-grant ids at 256; eligibility
instructions at 16. These limits must contain the instance's settings and saved data.
Instructions, fixed messages, summaries and repair explanations use `text_content`, so
large text can use a blob. Every serialized frame must still fit 262,144 bytes, including
JSON escaping and UTF-8 encoding. The receiver pages list rows to fit that budget and
refuses an oversized single command rather than truncating its values. The adapter must
check stored diagnostic JSON against its bound; these choices require acceptance tests
with the destination's saved data before switching the runtime to this contract.

### People, tasks, agent status and steering

`people.set_standing` returns the manager's actual work counts, including deleted
task records, Objectives and schedules, held and restored records, deleted sandboxes,
and team schedules moved to another administrator. Gateway-owned grant and access
request changes are not manager counts. A repeated command returns its saved result.

`tasks.inventory` pages a combined sequence of roots, then schedules, each ordered
by its id. `offset` and `limit` select that sequence; `total` counts both kinds.
For each returned root, `child_offset` and `child_limit` select children ordered by
task id, with `children_total` and `next_child_offset` to continue. Repeat the same
root window with the next child offset to read a larger graph. Senders may shorten
either window to fit the frame, but never silently discard members. The maximum
window is 100 roots or schedules and 200 children per root. Blockers use
`text_content` so the full waiting reason can be read from a blob when necessary. A root
also carries the request's live claims (`claims`, newest eight, with `claims_total`) and,
while one of its tasks waits, what for and until when (`waiting_for`: a resource, or another
of the person's requests with its title), so Settings → Tasks can show "waiting for Archive
cleanup until 10:45" ("Coordination between a person's requests").
Schedule entries retain `objective_id` for scheduled-Objective counts and may omit
their name, as today. `tasks.list` keeps blockers and latest activity;
`tasks.list_finished` keeps the owner's display name. Task ids in these lists are
the root task ids. Both list replies return `next_offset` only when more remain.
After a cancel or Objective control, the gateway reads the inventory again to show
the refreshed work list.

`agent.status` uses today's finding severities, `problem`, `warning` and `note`.
Context measurements are absent when unavailable, including an idle agent. Tools,
skills and findings may be absent in a basic answer. A full answer is allowed only
for the team's lead, checked against its current session by the receiver.
Per-mille values are the measured ratio multiplied by 1,000 and rounded to the
nearest integer. They may exceed 1,000 when a budget is exceeded; the contract
allows up to 1,000,000. The diagnostic JSON string stays bounded at 65,536 characters.

`intent.set` uses integer versions in its request, successful reply and
`changed_since_read.current_version`; a stale reply always includes that value.
For `steering.decide`, `type: person_as_is` carries no replacement text or
attachments. The team services copy the person's stored text, attachments and
replied message using `person_steering_id`. `type: guidance` with `source: lead`
carries the lead's own words. This prevents a lead's paraphrase from being sent
as the person's unchanged steering.

### Coordination between a person's requests

A person's requests can run at once and touch the same files and records. The `shared_work.*`
operations let an agent on any host see the person's other running requests, reserve what it
is about to change, leave a note for whoever comes next, and wait for a resource or a request
instead of working around it. The team services answer them from the registry of running work
(the change ledger's request rows, claims, notes and waits). Nothing here gives access: the
team services check every resource against what the task may reach before they read or record
anything, and answer `not_allowed` otherwise. No runtime sends these operations yet; this
section fixes their wire form so agents on other hosts can use them once they do.

**Who asks, for whom.** Only lead and worker hosts send these operations, for an agent, with
the token of the root task it works on (`authority_binding: {type: root_task}`). The body names
the agent's `task_id`; the team services check that the agent holds that task and that the
token is bound to its root task (`bad_authority`). The request is the token's root task, and
the person is the token's person. A request never waits on its own tasks, and a claim belongs
to the request, so the lead and every worker of one request act under it. Work for no person
takes part as team maintenance (below).

**What a request learns about others.** Awareness stays within one person, and team
maintenance is the team's own work:
- The person's own requests see each other in full: titles, states, reasons and note texts.
- Another person's request is "another team member's request" (`another_member`). A request
  learns only that it holds a claim on, above or under a resource the request named and until
  when; that notes exist there, without their text; how many requests wait for it
  (`waiting_requests`, a bare number that counts every request, so a refusal always shows its
  cause); and, when a wait is refused, that it waits for something this request holds
  (`would_loop`). Never its title, state, reason or note text, and never whether it waits for
  its person (`holder_waiting_for_person` is sent only for the person's own requests).
- Work for no person, a run of a schedule that works for nobody, is team maintenance
  (`team_maintenance`). It runs as the team, not as an administrator: it then keeps no person's
  access, reaches no person's private space, and does not move or stop when an administrator
  leaves. It has no private side either, so its claims show their reason and its notes their
  text to every request, after the same checks as everyone's. It may not name a resource in a
  person's own space (`not_allowed`) and may wait for resources but not for requests;
  `shared_work.count` answers zeros for it and `shared_work.list` shows only its own claims
  and waits.
- `shared_work.count` counts only the person's own other requests.

**Resource keys.** `resource_key` is one string, built by the host's trusted code from what the
agent named, never free text:
- `file:<folder target>`, with the folder target grammar of access grants (`team/...`,
  `agents/...`, `users/<folder>/...`, `data/<name>/...`): no empty, `.` or `..` part, no
  backslash and no control character. A folder key always ends with `/`, a top folder's too
  (`file:team/`, `file:users/<folder>/`), and a file key never does, so each file and folder
  has one spelling. A folder conflicts with every key under it: a claim on
  `file:team/reports/` conflicts with one on `file:team/reports/q3.md` (`relation` `above`
  and `below`);
- `record:knowledge_page:<space>:<page>`, `record:memory_fact:<bank>:<number>`,
  `record:schedule:<id>`, `record:objective:<id>` and `record:heartbeat_item:<id>`;
- `account:<tool>:<owner>`, the team's account of a tool or the person's own.

The schema checks the spelling. The team services also refuse, with `invalid_request`, a key
whose spelling is right but whose meaning is not: a folder named without its `/`, or a file
named with one.

A key in a person's own space (`record:knowledge_page:personal:<page>`,
`record:memory_fact:usermem:<number>`, `account:<tool>:person`) names the token person's own
record, since a person's space is never another person's to change. The team services keep and
compare these keys together with that person, so the same key from two people never conflicts
and never reveals that the other person works on something. Work for no person has no such
space and gets `not_allowed` for these keys.

Records are named the way people and agents name them, so a memory fact's number is given to
the next new fact once the fact is gone. A record is removed when it is deleted, and when its
store removes it after its end: a memory fact past its expiry time (`expires`), a schedule past
its end date (`expires_at`) or after its last run. In the step that removes a record, the
claims and notes on it end and every wait on it ends without a grant (`record_removed`, "Waits
and grants"). A record that later takes the same number is another resource and starts with no
claim, note or wait. Nothing is above or under a record key, so a removal ends nothing on
another key. A file key names a path, not a record: a file deleted and written again at the
same path is the same resource, and the claims, notes and waits on it go on.

**The operations.**
- `shared_work.count` gives the numbers for the line each turn of a person's work shows: the
  person's other running requests, how many of them are scheduled runs or hold claims, and how
  many of this request's tasks wait for another request.
- `shared_work.list` gives the asking request's own live claims and waits (`this_request`),
  whichever of its tasks took them, so a lead sees what its workers hold. It also gives the
  person's other running requests, a page at a time (`offset`, a `limit` of at most 64,
  `total`, and `next_offset` while more remain), with their kind, state, last activity, claims
  and notes.
- `shared_work.check` reports, for up to eight resources, the live claims on, above or under
  each one, its notes, and whether a wait on it would be accepted now (`can_wait`).
- `shared_work.claim` claims up to eight resources, all or none, for 15 minutes. It answers
  `claimed`, listing every conflict, when for one of them:
  - another request holds a live claim on, above or under it;
  - another request waits for something on, above or under it. A waiter keeps its place, so
    claims on the files in a folder never pass over a request that waits for the folder;
  - this request already holds a live claim on, above or under it, listed as `this_request`.
    The request uses, extends or releases that claim instead, so it holds a resource for at
    most 35 minutes at a time.

  Its answer carries the notes on the resources, grouped by resource.
- `shared_work.extend` adds 10 minutes, at most twice (`limit_reached` after that), so a claim
  lasts at most 35 minutes. Activity never extends a claim. A claim that has ended answers
  `not_found`, and a claim on a resource the task may no longer reach answers `not_allowed`.
- `shared_work.release` ends a claim now. Giving a claim up is never refused: a claim of this
  request that has already ended answers `ok` with the time it ended, and only a claim id that
  is not this request's answers `not_found`. A claim also ends, without a message, when its
  request ends, fails or is stopped, and when its record is removed ("Resource keys").
- `shared_work.note` leaves up to 500 characters on one resource, at most three per resource
  for each request (`limit_reached`). A note lasts while its request runs and one day more.
- `shared_work.wait` waits for a claimed resource or for another of the person's requests. A
  wait on a resource gives the `reason` its claim carries if the wait is granted. In one
  serialized step, in this order, it:
  - refuses a wait on a resource while this request holds a live claim on, above or under it
    (`holds_claim`), listing those claims as `shared_work.claim` lists its own (`this_request`).
    A grant would be a second claim over what the request already holds and would keep it held
    for up to 35 minutes more, so the request uses, extends or releases its claim instead, and
    waits only once it holds nothing there;
  - refuses a wait on the request itself or one that would close a loop (`would_loop`, naming
    what this request holds that the other one waits for);
  - answers `nothing_to_wait_for` when nothing but this request's own waits is on, above or
    under the resource.

  Otherwise it records the wait, answers with the latest time it ends (`ends_by`), and the host
  ends the turn with a local wait, freeing the agent's slot.

Notes and the reasons of claims and of waits on a resource are text a model wrote that other
models read. Both are checked like knowledge pages for credentials and identity numbers
(`sensitive_content`, from `note`, `claim` and `wait`) and shown to models as quoted text from
another request, never as instructions.

**Reply size.** Each list inside a coordination reply holds at most eight items, newest first,
next to a total that counts them all (`claims_total`, `notes_total`, `waits_total`,
`holding_total`); `shared_work.list` pages its requests ("Reply size"). A reply that would still
not fit in `max_frame_bytes` leaves out the oldest notes first, then the claims that end first,
never a resource it was asked about, and its totals still count everything.

**Waits and grants.** These rules keep every wait finite and free of loops:
- Every wait lasts at most 35 minutes, on a resource or on a request, and `ends_by` is that
  limit.
- The loop check follows who waits for whom. A waiting request waits for every other request
  that holds a live claim on, above or under what it waits for, for every other request whose
  earlier wait is on, above or under what it waits for, since that one is granted first, and,
  for a wait on a request, for that request. A wait that would make a request wait for itself
  through these is refused. So a later grant never closes a loop either: the request that gets
  a claim was already ahead of everyone it now blocks.
- Whenever a claim ends (released, ran out or its request ended) or a wait ends without a
  grant (its limit, or its task or request ended), the team services look at the waits on,
  above or under that resource in the order they were recorded. A wait is
  granted when no other request holds a live claim on, above or under its resource and no
  other request's earlier wait is on, above or under it. The grant is a new claim of the
  waiting request, with its own `claim_id`, on exactly the resource it waited for, with the
  wait's `reason`, for 15 minutes from the grant. The request's other waits on that resource
  or under it end with the same grant, each with its own `wait.ended`, so a request never
  waits on its own claim.
- When a record is removed ("Resource keys"), every wait on it ends without a grant, in the
  same step as the claims on it, each with its own `wait.ended` (`record_removed`). A wait on a
  removed record is never granted: the record it waited for is gone, and a record that later
  takes the same number is another resource, which the waiting request never asked for.
- A wait ends without a message when its task stops, fails or ends, moves to another holder
  or is handed back, and when its request ends, fails or is stopped. A claim already granted
  stays with the request, which sees it with `shared_work.list`.

Writes (`claim`, `extend`, `release`, `note`, `wait`) carry the agent's `request_id` as their
retry key ("Stored outcomes"); `count`, `list` and `check` are reads keyed by the message id.

**The end of a wait.** `wait.ended` is durable work from the team services to the holder of
the task that recorded the wait (`routing: holder`), so it survives restarts. It is sent once:
a wait ends without a message when its task moves or is handed back, so no other holder ever
needs it, and its key names the wait alone. It goes to the holder's control queue, which the
host reads even while every slot is busy or the agent is paused, like an access decision: the
host takes it at once and resumes the task ahead of new work as soon as a slot is free. It
wakes the model ("Waking the model"). It says why the wait ended:
- `claim_granted`: the wait was granted ("Waits and grants"): its new claim, with the notes on
  the resource. Its 15 minutes start when it is granted;
- `request_ended`: the request it waited for ended;
- `record_removed`: the record it waited for was deleted, or removed by its store after its end
  ("Resource keys"). The host knows the record from its wait. The model reads again before it
  changes anything there, since a record that later takes the same number is another record;
- `limit_reached`: the wait reached its 35 minutes. `still` says what it waited for is doing:
  `claimed` for a resource, `running` or `waiting_for_person` for a request. The model may
  carry on, wait again or ask the person.

A granted claim's `ends_at` is at most 15 minutes after the message (body rule `ends_within`).

**What the host does with a wait.**
- It repeats a `shared_work` write with the same `request_id` until it gets an outcome
  ("Stored outcomes"), before the model is told anything, so no wait or claim is recorded that
  the host does not know about. A repeated `wait` whose wait has already ended gets its stored
  `ok`, and the host then finds the `wait.ended` it kept.
- A `wait.ended` can arrive before the task's turn has ended with its wait, for example when
  the reply was slow. The host keeps it under the task and applies it when the turn ends with
  that wait, as it does for a stop that comes before its task.
- When it resumes a task whose granted claim's `ends_at` has passed, it tells the model that
  the claim has already ended.
- If no `wait.ended` has come by `ends_by` plus the clock tolerance, the host resumes the task
  as if the wait reached its limit, with what it waited for unknown, logs the task and the
  wait id, and ignores a later `wait.ended` for it. A lost or set-aside message then delays a
  task by the clock tolerance at most, never forever.
- The holder's work ledger opens the wait when `shared_work.wait` answers `ok`
  (`coordination_wait_open`) and closes it on `wait.ended` (`coordination_wait_closed`). For a
  delegated task, the team services also tell its requester with `ledger.fact` (`type: wait`,
  `kind` `claimed_resource` or `other_request`, `case_id` the wait id) when the wait opens and
  when it is resolved, so the requester's stand-in shows the held-up work.

**What the requester hears.** A worker's claims, extensions, releases and notes send nothing to
its lead. When something happened that the lead may need to plan around, trusted code adds
`coordination` events to the task's `task.result`, at most one of each kind (body rule
`unique`), each listing up to eight cases with how many there were in all, so a busy task never
runs out of room for them: its waits and how they ended, its refused waits and what they were
for, its writes refused because another request claimed the resource, its claims that ran out
after their last extension while the work was unfinished, and the resources it left notes on.
A worker that cannot go on asks its lead with `task.question`, like any other blocker.

## Covered changes

Two of a person's requests can run at once and change the same stored record. The stores
refuse a change that was based on an older read, and a change to a record that another
request changed while this one ran (`storage.change_ledger`). An operation that changes
such a record states `covered_change: {record_kind, seen_version}` in the registry. Only
request/reply operations have one, and the generator checks the operation's body, reply
and key against it.

**Record kinds.** `record_kind` is one of `covered_record_kinds`, which are the
store-safety code's `ChangeRecordKind` names; a test keeps the two lists equal.
- `memory_fact`, `knowledge_page`, `schedule`, `objective` and `heartbeat_item` each name
  one stored record.
- `staged_change` is a staged platform plan, which can change several records when it is
  applied.
- `file` has no operation yet. Files stay with the host that has the folder, and
  `record_busy` covers a file that another request is writing.

**The version the writer read.** `seen_version` in the body is the record's version as
the writer last read it. The registry value says who must send it:
- `required`: every sender sends it, and the body requires it. People's controls in the
  gateway already send the version they listed, for example the chat and page controls
  of schedules and Objectives.
- `required_for_request_writers`: every request writer must send it; a person's command
  through the gateway may leave it out, and then acts on the record it names without a
  check. Request writers are agents: a lead or worker host sends their frames for them,
  with a token bound to the root task the agent works on (a person's request or a
  scheduled run). This is today's rule for memory: agent tools must name the fact's
  version, and people's own commands name a fact by the number they see
  (`custom_agents.pinned_memory_runtime`).
- `optional`: any sender may send it, and the receiver checks it when it is given.
  `knowledge.write` works as today for every writer: without a version it creates a page,
  and is refused with `page_exists` when the name is taken; with one it edits the page
  while the page still has that revision (`knowledge_base.service`).
- `none`: there is no version, and the body has no `seen_version`. A create or a note has
  nothing to read first (`memory.create`, `objectives.create`, `heartbeat_items.add`,
  `knowledge.add_note`), and `memory.undo` names the event it reverses.

The body offers the field without requiring it for `required_for_request_writers`,
because a schema cannot tell an agent from a person. The receiver checks it: it refuses
an agent's change without a version with the operation's `invalid_request` reply, and
changes nothing. An operation that only creates a record has no version to send, so
`schedules.install` sends one when it changes a stored schedule.

Every sender, the operator's command line included, reads the record before it changes
it, and sends the version it read wherever the operation takes one. Today's `cron` and
`heartbeat` commands send none and must list first once they use these operations.

**What the version is.** The version is the store's own, as today's code computes it, and
it travels as a string:

| Record kind | Version |
| --- | --- |
| `memory_fact` | the fact's record digest (`pinned_memory_record_digest`): bank, owner, number, internal id and last change time, so a fact that later takes the same number has another one |
| `knowledge_page` | the page revision as a decimal string, such as `"3"` |
| `schedule` | the schedule's listing digest (`schedule_listing_digest`), which leaves out what runs change by themselves |
| `objective` | two digests today: people's controls compare a digest of the whole record, and the lead's updates compare `objective_version`, which leaves out status, progress and other bookkeeping so that running work does not refuse an agent's edit. The Objectives section of this README states which operation uses which |
| `heartbeat_item` | the item's version (`heartbeat_item_version`), a digest of its id, title, instruction, target agent type and Objective, never of its run times |
| `staged_change` | the staged plan's digest (`plan_digest`) that the staging tool returned; today `apply_change` refuses a plan whose digest changed after approval |

**Shared refusals.** A covered operation offers the shared refusals (`change_refusals`)
that can happen to it, each with its data:
- `changed_since_read` carries `current_version`, the record's version now. It is
  required wherever a writer may send a version, so the writer can read again and decide
  from what changed. `memory.undo` sends no version but can still be refused this way:
  today an undo is refused when the fact changed after the event or its number now holds
  another fact. Its `current_version` is absent when the number holds no fact. The
  creates cannot be stale, so they do not offer `changed_since_read`.
- `change_conflict` carries the conflict's `case_id` and its `brief`, a blob reference.
- `request_closed` may carry the request's state.
- `needs_person_decision` may carry the `case_id` the person decides in a change review
  ("Change reviews").
- `record_busy` carries `retry_at`, when to try again. When another request's claim on the
  record caused it ("Coordination between a person's requests"), it also carries `claim`: the
  claim's id and resource, when it ends (which is `retry_at`), whose kind of request holds it
  (the person's own, another team member's, or team maintenance) and how many notes are on
  the resource. Before the model sees the refusal, the host's trusted code reads the holder's
  description and the notes with `shared_work.check`, under the same privacy rules, so the
  model can wait, carry on with other work or ask the person. The refusal itself stays small
  in every covered operation.

`change_conflict`, `needs_person_decision` and `record_busy` come only from the checks of
covered records, so the generator refuses them on an operation without `covered_change`.
`changed_since_read` and `request_closed` also answer the lead's operations on its own
request (`intent.set`, `custody.decide`, `requests.pause`, `requests.resume`), which change
the request itself and no covered record.

These replies carry the stores' conflict cases, each with its `case_id` and `brief`.
Agent tool writes keep calling today's stores directly until they move onto these
operations together with the change review ("Change reviews"). Gateway commands may move
separately because the request-specific conflict rule does not refuse a person's own
edits.

## Stored outcomes

A request/reply operation that changes something is carried out once per command, however
often the sender retries it. Its retry key is its idempotency key, made from the parts its
registry entry lists ("Idempotency keys").

- **Stored with the change.** The receiver of a change operation stores the final outcome
  under the team and the retry key, in the same transaction as the change, before it
  replies. A repeat of the key gets the stored reply and changes nothing.
- **Kept 7 days.** The receiver keeps an outcome for at least 7 days, the longest
  lifetime of an authority token (`authority_token_max_seconds`).
- **Reads store nothing.** A read is keyed by `/message_id`, so every frame is a new read
  and a retry reads again.
- **Outcomes that ask for a retry are not stored.** For outcomes in `retry_outcomes` the
  receiver stores nothing, so a retry with the same key is decided again:
  - `not_started`: `tasks.steer` while the request still waits behind other work. Today
    the gateway holds such guidance and sends it again under the same id until the lead
    accepts it (`assistant_gateway.application.thread_guidance`), and the lead records
    an id only when it accepts the guidance (`custom_agents.task_steering_runtime`). A
    stored `not_started` would answer every later retry, and the guidance would be lost.
  - `record_busy`: another request is writing the file or sign-in; the reply says when
    to try again.
  - `waiting`: `staged_changes.apply` while the person has not decided yet.
  - `runtime_error`: the receiver failed, and its transaction changed nothing.
- **Fresh ids.** The ids in key parts (`request_id`, `steer_id` and the others) are made
  fresh by the sender for each new command, as a UUIDv7 or at least 128 random bits, and
  kept when the same command is retried. A sender never reuses one for another command.
  Keys do not name their sender: fresh ids keep two hosts' commands apart, and a retry
  that another gateway process sends (held guidance can move between them) still finds
  the stored outcome. The examples use short ids so that they are easy to read.
- **A repeated key with another body** is a sender defect. The receiver answers with
  the stored outcome, changes nothing, and logs both body digests.
- **No per-frame parts.** A retry is a new frame, so the key of a covered change never
  uses a part that changes with every frame: `/message_id`, `/idempotency_key`,
  `/issued_at`, `/not_before`, `/expires_at`, `/body_digest` or `/signature`. Such a key
  would never find the stored outcome. The generator refuses one.

## Reply size

A reply never exceeds `max_frame_bytes`, like every frame.
- A list reply returns fewer items than asked when more would not fit. It says how many
  items there are in all (`total`) and where to continue (`next_offset`), and the caller
  asks again from there. `next_offset` is present only when more items remain.
  Agent knowledge searches omit `total` because the existing search service
  provides continuation without a matching count, as described under Knowledge.
- The request says where to start and how many items it wants (`offset` and `limit`).
- Long text goes by blob reference wherever the schema offers `text_content`.
